# DX11 공부 정리(물방울책) - 15장

### Chapter15. 인스턴싱과 절두체 컬링

<details>
  <summary> 0. 인스턴싱과 절두체 컬링이란 </summary>

- **인스턴싱** : 똑같이 생긴 물체 여러 개를 **한 번의 Draw 호출**로 그리는 방법
- **절두체 컬링** : 카메라에 **안 보이는 물체는 아예 그리지 않는** 방법
- 책 예제는 둘을 합쳐서 해골 125개 중 보이는 것만 골라 한 번에 그린다.

> 비유 : 붕어빵 가게

- 일반 그리기 : 손님(CPU)이 사장님(GPU)에게 "붕어빵 하나 주세요"를 125번 따로 주문
- 인스턴싱 : "이 틀로 125개, 위치랑 색은 이 목록대로 주세요"라고 한 번에 주문
- 절두체 컬링 : 주문하기 전에 먹을 사람(화면에 보이는 것)만 골라서 주문

</details>

<details>
  <summary> 1. 하드웨어 인스턴싱 (15.1) </summary>

> 필요한 이유

- 같은 메쉬를 물체 수만큼 `DrawIndexed`로 그리면 **드로우 콜 오버헤드**(API, 드라이버 처리)가 CPU 병목이 된다.
- 사장님 손은 빠른데 **주문 받는 시간**이 오래 걸리는 것

> 정점 데이터와 인스턴스 데이터

- 정점 버퍼(슬롯 0) : 붕어빵 틀 모양. 모든 인스턴스가 같이 씀
- 인스턴스 버퍼(슬롯 1) : 주문 목록. 인스턴스마다 다른 값(월드 행렬, 색 등)

| |일반 그리기|인스턴싱|
|---|---|---|
|메쉬|매번 같은 메쉬|같은 메쉬|
|Draw 호출|물체 수만큼|**1번**|
|물체마다 다른 값|상수 버퍼를 매번 갱신|인스턴스 버퍼에 목록으로 한꺼번에|

- 인스턴스 버퍼도 결국 **정점 버퍼**다. (`D3D11_BIND_VERTEX_BUFFER`)

</details>

<details>
  <summary> 2. 정점 셰이더 (15.1.1) </summary>

```hlsl
struct VS_IN_INST
{
    float3 vPosition : POSITION;            // 정점마다 바뀜 (틀 모양)
    float3 vNormal   : NORMAL;
    float2 vTexCoord : TEXCOORD;
    row_major float4x4 matWorld : WORLD;    // 인스턴스마다 바뀜 (주문서 한 줄)
};

VS_OUT VS_MAIN_INST(VS_IN_INST In)
{
    VS_OUT Out;

    float4 vPosW = mul(float4(In.vPosition, 1.f), In.matWorld);   // g_matWorld 대신 In.matWorld
    Out.vPosW = vPosW.xyz;
    Out.vNormalW = mul(In.vNormal, (float3x3) In.matWorld);

    Out.vPosition = mul(mul(vPosW, g_matView), g_matProj);
    Out.vTexCoord = In.vTexCoord;
    return Out;
}
```

- 월드 행렬을 상수 버퍼(`g_matWorld`, 모든 정점이 같은 값)가 아니라 **정점 입력**(`In.matWorld`, 인스턴스마다 다른 값)으로 받는다.
- `VS_OUT`은 그대로 쓰기 때문에 PS는 수정할 필요가 없다.

> 전치 주의 (가장 실수하기 쉬운 부분)

- 상수 버퍼는 HLSL `cbuffer`의 기본값이 열 우선이라 C++에서 `XMMatrixTranspose`로 보냈다.
- 정점 입력은 C++ 메모리 바이트가 **그대로** 들어온다.
- 따라서 인스턴스 버퍼는 **전치하지 않고** 넣고, 셰이더에서 `row_major`로 받는다.
- 둘 다 하거나 둘 다 빼면 물체가 엉뚱한 곳에 찌그러져서 나온다.

</details>

  <summary> 3. 인스턴스 자료 스트리밍 - 입력 레이아웃 (15.1.2) </summary>

```cpp
typedef struct tagVtxNormInstance
{
    static constexpr uint32_t iNumElements = 7;
    static constexpr D3D11_INPUT_ELEMENT_DESC Elements[iNumElements] =
    {
        // 슬롯 0 : 정점마다
        { "POSITION", 0, DXGI_FORMAT_R32G32B32_FLOAT,    0, 0,  D3D11_INPUT_PER_VERTEX_DATA,   0 },
        { "NORMAL",   0, DXGI_FORMAT_R32G32B32_FLOAT,    0, 12, D3D11_INPUT_PER_VERTEX_DATA,   0 },
        { "TEXCOORD", 0, DXGI_FORMAT_R32G32_FLOAT,       0, 24, D3D11_INPUT_PER_VERTEX_DATA,   0 },
        // 슬롯 1 : 인스턴스마다
        { "WORLD",    0, DXGI_FORMAT_R32G32B32A32_FLOAT, 1, 0,  D3D11_INPUT_PER_INSTANCE_DATA, 1 },
        { "WORLD",    1, DXGI_FORMAT_R32G32B32A32_FLOAT, 1, 16, D3D11_INPUT_PER_INSTANCE_DATA, 1 },
        { "WORLD",    2, DXGI_FORMAT_R32G32B32A32_FLOAT, 1, 32, D3D11_INPUT_PER_INSTANCE_DATA, 1 },
        { "WORLD",    3, DXGI_FORMAT_R32G32B32A32_FLOAT, 1, 48, D3D11_INPUT_PER_INSTANCE_DATA, 1 },
    };
}VTXNORM_INSTANCE;
//                                         ↑슬롯        ↑오프셋                              ↑StepRate
```

|항목|의미|
|---|---|
|`PER_VERTEX_DATA`|정점마다 다음 칸으로|
|`PER_INSTANCE_DATA`|인스턴스마다 다음 칸으로|
|`InstanceDataStepRate`|인스턴스 몇 개마다 넘어갈지 (1이면 매번, 정점 데이터는 0)|

> WORLD를 4개로 나누는 이유

- 입력 원소 하나 = 정점 셰이더 입력 레지스터 한 칸 = **최대 128비트(float4, 16바이트)**
- `DXGI_FORMAT`에서 가장 큰 것이 `R32G32B32A32_FLOAT`(float4)이고, 행렬 포맷은 없다.
- 그래서 64바이트짜리 4x4 행렬을 16바이트씩 4줄로 나눠서 보낸다. (큰 가구를 상자 4개로 분해해서 엘리베이터에 싣는 것)
- 이름은 같고 **SemanticIndex**(두 번째 인자)만 0~3으로 다르다. (`TEXCOORD0`, `TEXCOORD1`과 같은 원리)
- 셰이더에서 `float4x4 : WORLD`로 선언하면 `WORLD0~3` 4칸을 연속으로 차지하고, `row_major`면 각 칸을 행으로 조립한다.

> 각 행에 들어가는 값

```
WORLD0 [ Right.x  Right.y  Right.z  0 ]   ← 오른쪽 축 (× 스케일 X)
WORLD1 [ Up.x     Up.y     Up.z     0 ]   ← 위쪽 축   (× 스케일 Y)
WORLD2 [ Look.x   Look.y   Look.z   0 ]   ← 앞쪽 축   (× 스케일 Z)
WORLD3 [ Pos.x    Pos.y    Pos.z    1 ]   ← 위치
```

- `CTransform`의 `STATE::RIGHT / UP / LOOK / POSITION`과 같은 구조
- 축은 방향이라 w = 0, 위치는 점이라 w = 1. 그래서 float3가 아니라 float4 4줄이다.
- 그림자 행렬처럼 투영이 섞인 행렬은 이렇게 깔끔하게 해석되지 않는다.

</details>

<details>
  <summary> 4. IA가 정점과 인스턴스를 짝짓는 방식 </summary>

- 버퍼에는 정점 한 세트(큐브 24개)와 인스턴스 값 16개가 있지만, **VS는 한 번 실행될 때 정점 1개 + 인스턴스 값 1개만** 받는다.
- 짝짓는 건 입력 조립기(IA)가 한다.

```cpp
// DrawIndexedInstanced(36, 16, ...) 의 내부 동작
for (instance = 0; instance < 16; ++instance)        // 바깥 : 인스턴스 (PER_INSTANCE, StepRate 1)
{
    for (i = 0; i < 36; ++i)                         // 안쪽 : 정점 (PER_VERTEX)
    {
        v = IndexBuffer[i];
        In.vPosition = VertexBuffer[v].Position;     // 슬롯 0
        In.matWorld  = InstanceBuffer[instance];     // 슬롯 1
        // SV_InstanceID = instance
        VS_MAIN_INST(In);
    }
}
```

|VS 호출|정점 (슬롯 0)|월드 행렬 (슬롯 1)|
|---|---|---|
|1 ~ 36번째|0 ~ 23번 정점|행렬 0|
|37 ~ 72번째|같은 0 ~ 23번 정점|행렬 1|
|...|...|...|
|541 ~ 576번째|같은 0 ~ 23번 정점|행렬 15|

- 정점 데이터는 16번 재사용되고, 월드 행렬은 36번씩 같은 값이 반복된다.
- 도장(정점 버퍼) 하나와 찍을 위치 목록(인스턴스 버퍼) 16줄. 목록 한 줄마다 도장 전체를 한 번 찍는다.
- 실제 GPU는 병렬로 처리하고 정점 캐시도 쓰지만, 어떤 정점과 어떤 행렬이 짝지어지는지는 위와 같다.

</details>

<details>
  <summary> 5. SV_InstanceID </summary>

- 지금 몇 번째 인스턴스를 그리는 중인지 나타내는 번호 (0 ~ N-1)
- `SV_`로 시작하는 **시스템 값**이라 IA가 만들어 준다. C++ 입력 레이아웃에 추가하지 않는다.
- 구조체 안에 넣어도 되고, 매개변수로 따로 받아도 된다. 셰이더가 보는 건 시맨틱이라 이름과 순서는 상관없다.

```hlsl
VS_OUT VS_MAIN_INST(VS_IN_INST In, uint iInstanceID : SV_InstanceID)
```

- 정점 셰이더에서만 받을 수 있다. PS에서 필요하면 `nointerpolation`을 붙여서 직접 넘긴다. (정수 번호를 보간하면 안 됨)

```hlsl
nointerpolation uint iInstanceID : INSTANCEID;
```

> 사용 예

|용도|번호를 무엇에 쓰는지|
|---|---|
|텍스처 배열|몇 번째 텍스처를 쓸지 (`Texture2DArray`, uv의 z = 번호)|
|구조적 버퍼|몇 번째 칸의 데이터를 꺼낼지 (인스턴스 버퍼 대신 `StructuredBuffer[iID]`)|
|위치 계산|원형, 격자처럼 규칙으로 배치할 때 번호로 위치를 직접 계산|
|변화 주기|흔들리는 타이밍, 색을 인스턴스마다 다르게|
|디버깅|번호별로 색칠해서 순서 확인|

- 구조적 버퍼 방식은 `WORLD0~3`처럼 입력 레이아웃을 쪼갤 필요가 없고 입력 원소 개수 제한(32개)에서도 자유로워서 실무에서 자주 쓴다.

> 주의

- `DrawIndexedInstanced`의 `StartInstanceLocation`을 써도 `SV_InstanceID`는 **0부터** 시작한다.
- 인스턴스 버퍼는 시작 위치부터 읽지만, 번호에는 시작 위치가 더해지지 않는다.

</details>

<details>
  <summary> 6. 인스턴스 자료 그리기와 버퍼 만들기 (15.1.3, 15.1.4) </summary>

> 그리기

```cpp
ID3D11Buffer* pVBs[]     = { m_pVB.Get(), pInstanceVB };
uint32_t      iStrides[] = { sizeof(VTXNORM), sizeof(float4x4_t) };
uint32_t      iOffsets[] = { 0, 0 };
m_pContext->IASetVertexBuffers(0, 2, pVBs, iStrides, iOffsets);   // 슬롯 0, 1 동시에

m_pContext->DrawIndexedInstanced(
    m_iIndexCnt,     // IndexCountPerInstance : 메쉬 하나의 인덱스 수
    iInstanceCnt,    // InstanceCount         : 몇 개 그릴지
    0,               // StartIndexLocation
    0,               // BaseVertexLocation
    0);              // StartInstanceLocation
```

- 인덱스 버퍼가 없으면 `DrawInstanced`
- 다른 오브젝트가 슬롯 0만 다시 꽂아도 슬롯 1에 인스턴스 버퍼가 남아 있는데, 그 오브젝트의 입력 레이아웃은 슬롯 1을 읽지 않으니 문제없다.

> 버퍼 만들기

- 물체가 움직이지 않고 컬링도 안 하면 `IMMUTABLE`로 한 번만 만들면 된다.
- 컬링을 하면 보이는 목록이 매 프레임 바뀌므로 `DYNAMIC`으로 만들고 `Map(WRITE_DISCARD)`로 갱신한다.

```cpp
D3D11_BUFFER_DESC desc{};
desc.ByteWidth      = sizeof(float4x4_t) * m_iNumInstance;   // 최대 개수만큼
desc.Usage          = D3D11_USAGE_DYNAMIC;
desc.BindFlags      = D3D11_BIND_VERTEX_BUFFER;
desc.CPUAccessFlags = D3D11_CPU_ACCESS_WRITE;                // DYNAMIC이면 필수
m_pDevice->CreateBuffer(&desc, nullptr, &m_pInstanceVB);     // 내용은 매 프레임 채우므로 초기 데이터 없음
```

|Usage|CPUAccessFlags|용도|
|---|---|---|
|`IMMUTABLE`|0이어야 함|한 번 만들고 안 바뀜 (초기 데이터 필수)|
|`DEFAULT`|0이어야 함|CPU는 `UpdateSubresource`로만 갱신|
|`DYNAMIC`|**`WRITE` 필수**|CPU가 `Map`으로 자주 갱신|
|`STAGING`|`READ`나 `WRITE`|GPU ↔ CPU 복사용 (12장)|

- `WRITE_DISCARD` : "이전 내용은 버리고 새 종이 달라". GPU가 이전 내용을 읽는 중이어도 기다리지 않는다. (12장의 `MAP_READ`가 GPU를 기다려서 느렸던 것과 반대)
- 원본 목록은 CPU 사본으로 따로 보관한다. 컬링할 때 이 사본을 읽어야 하기 때문 (책의 `mInstancedData`)

</details>

  <summary> 7. 인스턴싱에서 노멀 변환 (역전치 행렬) </summary>

|월드 행렬 구성|`(float3x3)World`로 노멀 변환|
|---|---|
|이동|가능 (3x3 부분에 영향 없음)|
|회전|가능 (회전 행렬은 역전치 = 자기 자신)|
|균일 스케일|가능 (길이만 바뀌고 `normalize`로 복구)|
|**비균일 스케일**|**불가 → 역전치 필요**|

> 방법 1 : 역전치 행렬도 인스턴스 데이터로 보내기

```cpp
typedef struct tagInstanceData
{
    float4x4_t  matWorld;               // 0 ~ 63    → WORLD0~3
    float4x4_t  matWorldInvTranspose;   // 64 ~ 127  → WORLDINVT0~3 (오프셋 64, 80, 96, 112)
}INSTANCE_DATA;

XMMATRIX matNoTrans = matWorld;
matNoTrans.r[3] = XMVectorSet(0.f, 0.f, 0.f, 1.f);
XMMATRIX matInvT = XMMatrixTranspose(XMMatrixInverse(nullptr, matNoTrans));   // 역전치의 "전치"는 수학 계산이라 함
XMStoreFloat4x4(&Datas[i].matWorldInvTranspose, matInvT);                     // 업로드용 전치는 안 함 (row_major)
```

- 같은 입력 레이아웃을 쓰는 다른 버퍼(그림자)도 구조체 크기를 맞춰야 한다.
- 노멀에는 3x3만 쓰니 3줄만 보내도 된다.

> 방법 2 : 셰이더에서 외적으로 계산

```hlsl
float3 r0 = In.matWorld[0].xyz;
float3 r1 = In.matWorld[1].xyz;
float3 r2 = In.matWorld[2].xyz;
float3x3 matCof = float3x3(cross(r1, r2), cross(r2, r0), cross(r0, r1));   // 여인수 행렬 = 역전치 × det
Out.vNormalW = mul(In.vNormal, matCof);                                     // normalize하니 det는 무시
```

- HLSL에는 `inverse()`가 없다.
- 음수 스케일(거울)이 있으면 det가 음수라 노멀이 뒤집힌다.

</details>

<details>
  <summary> 8. 인스턴싱 vs 기하 셰이더 </summary>

- 둘 다 Draw 한 번으로 물체 여러 개를 그린다. 차이는 **모양을 어디서 가져오느냐**
- 인스턴싱 : 완성된 **도장**(메쉬)을 목록 위치마다 찍는다.
- 기하 셰이더 : **씨앗**(점)을 뿌려 두면 GPU가 그 자리에서 모양을 키워 낸다.

```
[인스턴싱 - Cube_Instance]  IA ──▶ VS (24정점 × 16번)           모양은 이미 있음
[기하 셰이더 - Tree]        IA ──▶ VS (16번) ──▶ GS (점 → 사각형)  모양을 새로 만듦
```

| |인스턴싱|기하 셰이더|
|---|---|---|
|모양|아무 메쉬나|GS가 코드로 만들 수 있는 단순한 모양|
|매 프레임 바뀌는 모양|어려움|쉬움 (카메라 방향 빌보드)|
|GPU 안에서 거르기|어려움|가능 (`Append` 안 하면 됨)|
|성능|매우 좋음|상대적으로 느림 (출력 정리 비용, `maxvertexcount` 제한)|

- 나무 빌보드는 실무에서 **사각형 1개를 인스턴싱하고 VS에서 빌보드 회전**을 계산하는 방식을 많이 쓴다.
- `SV_VertexID`(0~3)로 사각형 모서리를 만들고, 나무 위치와 크기는 인스턴스 데이터로 받아서 `DrawInstanced(4, 나무 수, 0, 0)` (12장 + 15장)

</details>

<details>
  <summary> 9. 경계 입체 (15.2) </summary>

> 비유 : 택배 상자

- 정점 수천 개를 하나하나 검사하는 대신 물체를 감싼 단순한 상자로 검사한다.
- 상자가 안 보이면 안에 든 물체도 확실히 안 보인다.

> XNA Collision → DirectXCollision (15.2.1)

|책 (XNA)|DirectXCollision|
|---|---|
|`XNA::AxisAlignedBox`|`BoundingBox`|
|`XNA::Sphere`|`BoundingSphere`|
|`XNA::Frustum`|`BoundingFrustum`|
|`ComputeFrustumFromProjection`|`BoundingFrustum::CreateFromMatrix`|
|`IntersectAxisAlignedBoxFrustum`|`box.Intersects(frustum)`|

> AABB (15.2.2)

- 면이 x, y, z 축과 나란한 상자. 정점들의 min/max로 만든다.
- DirectXCollision은 (중심, 반 크기)로 저장한다.

```cpp
XMVECTOR vMin = XMVectorReplicate(+FLT_MAX);   // 첫 정점이 무조건 갱신되도록
XMVECTOR vMax = XMVectorReplicate(-FLT_MAX);
for (const auto& tVtx : vertices)
{
    vMin = XMVectorMin(vMin, XMLoadFloat3(&tVtx.vPosition));
    vMax = XMVectorMax(vMax, XMLoadFloat3(&tVtx.vPosition));
}
XMStoreFloat3(&m_tLocalBox.Center,  0.5f * (vMin + vMax));
XMStoreFloat3(&m_tLocalBox.Extents, 0.5f * (vMax - vMin));

// 한 줄 버전
BoundingBox::CreateFromPoints(m_tLocalBox, size(vertices), &vertices[0].vPosition, sizeof(VTXNORM));
```

- 회전시키면 상자가 기울어져서 더 이상 축 정렬이 아니게 되고, 다시 AABB로 감싸면 헐거워진다.
- 해결책 : **상자는 로컬에 그대로 두고 절두체를 로컬로 데려온다.** (15.3)

> 구 (15.2.3)

- 중심 : AABB 중심, 반지름 : 중심에서 가장 먼 정점까지 거리
- 회전해도 그대로라 편하지만, 길쭉한 물체는 빈 공간이 많다.

> AABB 계산은 어디서?

|시점|하는 일|
|---|---|
|`Initialize_Prototype`|정점 배열을 만든 직후 로컬 AABB 계산 (한 번, 클론은 복사받음)|
|매 프레임 `Late_Update`|이미 만든 박스와 절두체를 비교만 함|

- 정점 배열은 지역 변수이고 정점 버퍼는 `IMMUTABLE`이라 CPU에서 다시 못 읽으므로, **정점 배열이 살아 있을 때** 계산해야 한다.
- 메쉬를 컴포넌트로 분리하면 메쉬 컴포넌트가 박스를 계산하고 보관한다. (박스는 메쉬 모양에만 의존)
- 박스가 실제보다 작으면 **보이는 물체가 사라지는 버그**, 크면 성능만 조금 손해. 애매하면 크게 잡는다.

<details>
  <summary> 10. 절두체 (15.2.4) </summary>

> 비유 : 손전등 불빛

- 카메라가 볼 수 있는 영역. 끝이 잘린 피라미드 모양
- 6개 평면(근, 원, 좌, 우, 상, 하)으로 둘러싸여 있다.

> 뷰 행렬과 투영 행렬의 역할

|행렬|절두체에서 맡는 역할|
|---|---|
|투영 행렬|**모양** : 시야각, 종횡비, near, far (손전등 설계도)|
|뷰 행렬의 역행렬|**위치와 방향** : 카메라가 어디서 어디를 보는지 (손전등을 들고 비추는 곳)|

```cpp
BoundingFrustum::CreateFromMatrix(m_tViewFrustum, matProj);   // 투영 행렬만 → 뷰 공간 절두체 (원점, +z)
XMStoreFloat4x4(&m_MatInvView, XMMatrixInverse(nullptr, matView));
```

- `CreateFromMatrix`에는 View x Proj가 아니라 **투영 행렬만** 넣는다.
- 만들고 나면 투영 행렬의 정보는 `Origin`, `Orientation`, `Slope`, `Near`, `Far` 같은 **도형 데이터**로 바뀐다.

> 평면 만들기 (15.2.4.1)

- 투영 결과가 `-w ≤ x ≤ w`, `-w ≤ y ≤ w`, `0 ≤ z ≤ w`이면 보인다.
- 이 부등식을 투영 행렬의 열(c1~c4)로 풀면 평면이 나온다.

|평면|식|
|---|---|
|왼쪽 / 오른쪽|c4 + c1 / c4 - c1|
|아래 / 위|c4 + c2 / c4 - c2|
|근 / 원|c3 / c4 - c3|

> 교차 검사 (15.2.4.2, 15.2.4.3)

- 평면 (n, d)와 점 p : `n·p + d`의 부호로 앞뒤 판정 (책은 법선이 안쪽을 향함)
- 구 : `n·c + d < -r`이면 구 전체가 평면 뒤 → 탈락
- AABB : 법선 방향으로 가장 안쪽 모서리 Q 하나만 본다. Q도 바깥이면 상자 전체가 바깥 → 탈락

```
각 축 j :  n_j ≥ 0 이면 Q_j = max_j,  아니면 Q_j = min_j
n·Q + d < 0  → 탈락
```

- 벽 6개 중 **하나라도 완전히 넘어가 있으면** 탈락
- 평면을 따로 검사하기 때문에 절두체 모서리 근처에서 가끔 잘못 통과시키지만(가짜 양성), 보이는 걸 버리는 실수는 없다. 잘못 통과한 건 GPU 클리핑이 처리한다.

</details>

  <summary> 11. 절두체 컬링 (15.3) </summary>

> 클리핑이 있는데 컬링하는 이유

- 비유 : 공연장 **입구에서 표 검사** vs 무대 앞에서 쫓아내기
- 클리핑은 정점 셰이더를 **다 실행한 뒤**에 일어난다.
- 컬링은 CPU에서 상자 하나로 검사해서 입장 자체를 막는다.

> 절두체를 로컬로 옮기기 (산을 옮기지 말고 내가 간다)

- 박스는 로컬, 절두체는 뷰 공간에 있다.
- 박스를 옮기면 축 정렬이 깨지므로 **절두체를 박스의 로컬 공간으로** 옮긴다.

```
[정점을 그릴 때]  로컬 ──World──▶ 월드 ──View──▶ 뷰 ──Proj──▶ 클립
[컬링할 때]       로컬 ◀──World⁻¹── 월드 ◀──View⁻¹── 뷰 (절두체 출발점)
```

```cpp
matrix_t matToLocal = XMMatrixMultiply(matInvView, matInvWorld);   // 행 벡터라 왼쪽부터 : View⁻¹ 다음 World⁻¹

vector_t vScale, vRotQuat, vTrans;
XMMatrixDecompose(&vScale, &vRotQuat, &vTrans, matToLocal);        // 크기 / 회전(쿼터니언) / 이동으로 분해

BoundingFrustum tLocalFrustum;
tViewFrustum.Transform(tLocalFrustum, XMVectorGetX(vScale), vRotQuat, vTrans);

return tLocalBox.Intersects(tLocalFrustum);
```

> 투영 행렬을 안 곱하는 이유

- 투영 행렬은 절두체 **모양**을 만들 때 이미 썼다.
- 절두체는 이미 뷰 공간에 놓인 도형이라, 옮기는 데는 위치와 방향을 바꾸는 행렬(View⁻¹, World⁻¹)만 필요하다.
- 투영 행렬은 뷰 공간을 클립 공간으로 찌그러뜨리는 변환이라 방향이 다르다.
- 반대로 박스를 World x View x Proj로 클립 공간에 보내서 검사하는 방법도 있다. 그때는 투영 행렬을 쓴다.

> XMMatrixDecompose

- 행렬 하나에 섞인 S x R x T를 크기, 회전, 이동 벡터로 다시 나눠 준다.
- 책의 `Transform`이 행렬이 아니라 조각(크기 float, 회전 쿼터니언, 이동)으로 받기 때문에 필요하다.
- 크기를 **float 하나**만 받으니 **균일 스케일까지만** 정확하다.
- `matToLocal`의 크기는 월드 스케일의 역수 (물체가 2배면 0.5)
- DirectXCollision에는 `Transform(Out, matToLocal)`처럼 행렬을 바로 받는 버전도 있다. (XNA에는 없었음)

> 책 코드 주의

- `XMMatrixInverse(&XMMatrixDeterminant(W), W)`는 임시 객체의 주소를 넘겨서 표준 C++에서는 에러. 행렬식이 필요 없으면 `nullptr`

bool_t CGameObject::Is_BoxInFrustum(const BoundingBox& tLocalBox, const XMMATRIX& matWorld)
{
    auto pCam = CGameInstance::Get().Get_MainCamera();
    matrix_t matInvView  = XMLoadFloat4x4(&pCam->Get_InvView());
    matrix_t matInvWorld = XMMatrixInverse(nullptr, matWorld);
    matrix_t matToLocal  = XMMatrixMultiply(matInvView, matInvWorld);

    vector_t vScale, vRotQuat, vTrans;
    XMMatrixDecompose(&vScale, &vRotQuat, &vTrans, matToLocal);

    BoundingFrustum tLocalFrustum;
    pCam->Get_ViewFrustum().Transform(tLocalFrustum, XMVectorGetX(vScale), vRotQuat, vTrans);

    return tLocalBox.Intersects(tLocalFrustum);
}

bool_t CGameObject::Is_InFrustum()
{
    if (false == m_bUseCulling)          // 기본은 꺼 둠 → 기존 오브젝트에 영향 없음

}

  <summary> 13. 프로젝트 적용2 - 그림자 컬링과 항등 행렬 </summary>

> 그림자를 따로 검사하는 이유

- 큐브는 화면 밖인데 **그림자만 화면 안에 걸치는** 경우가 있다.
- 큐브 결과로 그림자까지 막으면 화면 가장자리에서 그림자가 툭 사라진다.

> 그림자는 월드 공간 박스로

- 그림자 행렬은 큐브를 평면에 납작하게 누르는 행렬이라 **역행렬이 없다.** (행렬식 = 0, 높이 정보가 사라짐)
- 그래서 로컬 박스에 그림자 행렬을 곱해서 **월드 공간 박스**를 만들어 둔다.
- `BoundingBox::Transform`은 꼭짓점 8개를 변환해서 다시 감싸기 때문에 그림자 행렬에도 쓸 수 있다.

> 월드 행렬 자리에 항등 행렬을 넣는 이유

- `Is_BoxInFrustum`의 행렬은 **"박스가 있는 공간 → 월드"** 로 가는 행렬이다.
- 박스가 이미 월드에 있으니 월드로 가는 데 아무 변환도 필요 없다. → 항등 행렬
- `View⁻¹ × I⁻¹ = View⁻¹` 이므로 절두체를 **월드까지만** 내린다.

```
박스를 로컬에 두었다 → 그 물체의 월드 행렬   (큐브)
박스를 월드에 두었다 → 항등 행렬             (그림자, 나무)
```

- 그림자 행렬을 넣으면 역행렬이 없어서 판정이 엉망이 되고, 큐브 월드 행렬을 넣으면 이동이 두 번 적용된다.

> CCube 그림자

> Tree가 다른 점

- **정점 1개 = 나무 1그루**. 점 16개를 `Draw(16)` 한 번으로 그려서 인스턴싱과 구조가 비슷하다.
- 점 위치가 **이미 월드 좌표**이고 셰이더도 `g_matWorld`를 안 쓴다. → 항등 행렬
- 실제 모양(16x16 사각형)은 GS가 만든다. 정점으로 박스를 만들면 크기가 0이므로 **GS가 펼칠 크기를 직접 반영**해야 한다.

> 나무 박스 크기

```
위에서 본 모습 (xz)        옆에서 본 모습
  ┌─────────┐              ┌───┐ ← +halfH
  │   ╲     │              │ ● │ ← 중심 (vPos)
  │    ●    │              └───┘ ← -halfH
  │     ╲   │
  └─────────┘  사각형이 y축으로 카메라를 향해 돌아도 중심에서 halfW 안에 있음
```

- 중심 : `vPos` (GS가 `Center ± halfHeight × up`으로 펼침)
- 반 크기 : `(halfW, halfH, halfW)` → 크기 16이면 `(8, 8, 8)`

```cpp
// Initialize
m_Trees[i].vPos = XMFLOAT3(x, y, z);
m_Trees[i].Size = XMFLOAT2(16.0f, 16.0f);
m_TreeBoxes[i]  = BoundingBox(m_Trees[i].vPos, float3_t(0.5f * m_Trees[i].Size.x, 0.5f * m_Trees[i].Size.y, 0.5f * m_Trees[i].Size.x));
// 정점 버퍼 : DYNAMIC + CPU_ACCESS_WRITE

// Late_Update
for (uint32_t i = 0; i < m_iTreeCnt; ++i)
    if (Is_BoxInFrustum(m_TreeBoxes[i], XMMatrixIdentity()))
        pDst[m_iVisibleCnt++] = m_Trees[i];

// Render_Mesh
m_pContext->Draw(m_iVisibleCnt, 0);
```

> 주의

- 컬링하면 보이는 나무만 앞에서부터 다시 채우므로 **`SV_PrimitiveID`가 매 프레임 바뀐다.**
- `PrimID % 4`로 텍스처 배열을 고르면 카메라를 돌릴 때마다 나무 텍스처가 바뀐다. → 텍스처 번호를 정점 데이터에 넣어야 함
- GS 안에서 `Append`를 안 해서 거를 수도 있지만, VS/GS 비용을 이미 쓴 뒤라 CPU에서 미리 빼는 게 낫다.
