# DX11 공부 정리(물방울책) - 12장

### Chapter12. 계산 셰이더 - 블러

<details>
  <summary> 0. 계산 셰이더란 </summary>

- **기존의 렌더링 파이프라인을 거치지 않고 GPU 일꾼들에게 직접 일을 시키는 방법**
- 데이터를 읽고, 계산하고, 써라
- 결과는 GPU 메모리에 그대로 남으므로, 바로 다음 그리기에 사용할 수 있다.
- GPU를 그래픽 외의 범용 계산에 사용하는 것을 GPGPU(General-Purpose GPU)라고 부름

</details>

<details>
  <summary> 1. 스레드와 스레드 그룹 </summary>

- 스레드 : 일꾼 한 명
- 스레드 그룹 : 일꾼 팀
- 스레드 그룹(일꾼 팀)이 있는 이유는 공용 작업대(공유 메모리)를 사용할 수 있기 때문, 팀원끼리 다 같이 기다리기가 가능하다.
- `[numthreads(16, 16, 1)]` : 팀 하나에 몇 명 넣을지(셰이더 코드에서 작성)

```hlsl
[numthreads(16, 16, 1)]    // 팀 하나 = 가로 16 × 세로 16 = 256명
void CS(...)
```

- `Dispatch` : `Dispatch`는 작업 지시서를 GPU에 넘기는 **실행 버튼**이다. 몇 팀을 투입할지 C++에서 정함
```cpp
m_pContext->Dispatch(80, 45, 1);    // 가로 80팀 × 세로 45팀 투입
```

> 총 스레드 수

```
총 일꾼 수 = Dispatch 팀 개수 × numthreads 팀 크기
          = (80 × 45) × (16 × 16)
          = 3,600팀 × 256명
          = 921,600명 = 1280 × 720 픽셀
```

- 팀 크기는 공유 메모리 크기에 영향을 주므로 셰이더 컴파일 때 정해져 있어야 하고, 팀 개수는 데이터 크기에 따라 달라지므로 C++에서 정한다.
- 팀 개수는 데이터를 다 덮도록 올림해서 계산함 -> `(픽셀 수 + 팀크기 - 1) / 팀크기`

> 팀 크기는 64의 배수로

- GPU는 일꾼을 내부적으로 소대 단위로 움직인다. (NVIDIA 워프 32명, AMD 웨이브프론트 64명)
- 팀 크기가 소대 크기의 배수가 아니면 빈자리가 생겨 낭비가 생김
- 따라서 팀 크기는 64의 배수로 하는 것이 좋다. (책은 256 사용)

</details>

<details>
  <summary> 2. 간단한 계산 셰이더(텍스처 더하기) </summary>

```hlsl
Texture2D           gInputA;    // 읽을 창고 1
Texture2D           gInputB;    // 읽을 창고 2
RWTexture2D<float4> gOutput;    // 쓸 창고

[numthreads(16, 16, 1)]
void CS(int3 dispatchThreadID : SV_DispatchThreadID)
{
    gOutput[dispatchThreadID.xy] = gInputA[dispatchThreadID.xy]
                                 + gInputB[dispatchThreadID.xy];
}
```

- `SV_DispatchThreadID` : 스레드 전체 좌표
- `Texture2D` : 입력 자원(SRV)
- `RWTexture2D` : 출력 자원(UAV)
- `[numthreads]` : 팀 크기
- 일꾼 번호(`SV_DispatchThreadID`)를 곧 담당 픽셀 좌표로 사용하는 것이 계산 셰이더의 가장 기본 패턴이다.
- 함수 안에 반복문이 없어도 일꾼 수만큼 동시에 실행되기 때문에 텍스처 전체가 처리됨
- 셰이더 모델은 `cs_5_0`, C++에서는 `CreateComputeShader`로 만들고 `CSSetShader`로 장착한다.

</details>

<details>
  <summary> 3. 입력과 출력 자원 </summary>

> 텍스처와 뷰

- 텍스처(`ID3D11Texture2D`) : 일종의 창고. GPU 메모리의 데이터 덩어리
- 뷰 : 출입증, "이 텍스처(창고)를 이런 용도로 써도 된다"라는 증명서
- 같은 텍스처에 출입증을 여러 장 발급할 수 있고, 어떤 출입증을 발급할 수 있는지는 텍스처를 만들 때 `BindFlags`로 미리 신고한다.

|출입증|의미|용도|
|---|---|---|
|SRV (Shader Resource View)|열람증|셰이더가 읽기|
|RTV (Render Target View)|그리기 허가증|파이프라인 그리기|
|UAV (Unordered Access View)|자유 출입증|셰이더가 직접 읽고 쓰기|
|DSV (Depth Stencil View)|깊이 기록증|깊이/ 스텐실 버퍼|

> 텍스처 입력

- SRV로 읽기
```hlsl
Texture2D g_Input : register(t0);
```
```cpp
m_pContext->CSSetShaderResources(0, 1, &pSRV); // PS가 아닌 CS에 바인딩
```
- 셰이더 단계마다 슬롯이 따로 있기 때문에 PS의 t0과 CS의 t0은 서로 다른 자리이다.

> 텍스처 출력과 UAV

- PS는 색을 return하면 출력 병합기가 받아서 렌더타겟의 픽셀에 써준다.
- 계산 셰이더에서는 결과를 내보내는 곳이 없다. (함수 반환형도 `void`)
- 따라서 CS의 결과는 UAV(Unordered Access View)를 통해 텍스처에 직접 써야 한다.
```hlsl
RWTexture2D<float4> g_Output : register(u0);  // RW = Read/Write

g_Output[좌표] = 결과;      // 배열에 대입하듯 직접 씀
```

- Unordered Access : 일꾼들이 정해진 순서 없이, 원하는 위치에 자유롭게 접근한다는 뜻
- UAV를 만들때는 보통 SRV도 같이 만든다. CS가 만든 텍스처를 다른 셰이더에서 읽어야 하기 때문.
```cpp
desc.BindFlags = D3D11_BIND_SHADER_RESOURCE      // 나중에 읽을 거면
               | D3D11_BIND_UNORDERED_ACCESS;    // ← UAV 발급 가능하게 신고
m_pDevice->CreateTexture2D(&desc, nullptr, &pTex);
m_pDevice->CreateUnorderedAccessView(pTex.Get(), nullptr, &pUAV);
```
```cpp
m_pContext->CSSetUnorderedAccessViews(0, 1, &pUAV, nullptr);   // u0에 바인딩
```

> 같은 텍스처를 동시에 읽고 쓰면 안 된다

- 같은 텍스처의 뷰가 입력(SRV)과 출력(UAV/RTV)에 동시에 묶이면 안 되므로, 사용한 뒤 nullptr로 뽑아야 한다.
- 뷰를 같이 만드는 것 자체는 문제가 아님. 동시에 **묶이는 것**이 문제

|상황|D3D 런타임 처리|
|---|---|
|입력으로 묶인 걸 출력으로 또 묶음|입력 쪽을 강제로 뽑음 (경고)|
|출력으로 묶인 걸 입력으로 또 묶음|새 입력을 무시함 -> 검은 화면|

```cpp
ID3D11ShaderResourceView* pNullSRV[1] = { nullptr };
m_pContext->CSSetShaderResources(0, 1, pNullSRV);   // 배열(이중 포인터)을 받기 때문에 nullptr을 바로 넣으면 안 됨
```

> 인덱싱과 샘플링

- 인덱싱 : 칸 번호로 정확히 그 텍셀을 꺼냄 (`Load`와 같음)
```hlsl
float4 c = g_Input[int2(100, 50)];            // 100열 50행
float4 c = g_Input.Load(int3(100, 50, 0));    // 같은 의미, 마지막 0은 밉 레벨
```
- 범위 밖을 읽으면 0(검은색)이 나오고, 범위 밖에 쓰면 무시된다.
- 그래서 일꾼이 데이터보다 많아도 터지지 않지만, 블러처럼 이웃을 읽는 경우에는 가장자리에 검은색이 섞이므로 `max`/`min`으로 막아야 함

- 샘플링 : 0~1 UV 좌표 + 샘플러로 주변 텍셀을 필터링해서 읽음
```hlsl
float4 c = g_Input.SampleLevel(g_Sampler, vUV, 0);    // Sample이 아니라 SampleLevel
```
- `Sample`은 화면에서 옆 픽셀과의 UV 차이를 보고 밉 레벨을 자동으로 고르는데, 계산 셰이더에는 화면도 옆 픽셀도 없음
- 따라서 CS에서는 밉 레벨을 직접 지정하는 `SampleLevel`을 사용해야 한다.
- 픽셀 좌표 -> UV 변환할 때 `+0.5`를 해야 텍셀의 정중앙을 읽는다.
```hlsl
float2 vTexelSize = 1.f / float2(iWidth, iHeight);
float2 vUV = (float2(vDispatchThreadID.xy) + 0.5f) * vTexelSize;
```
- 샘플러를 `CLAMP`로 만들면 범위 밖 UV를 가장자리 텍셀로 고정해주기 때문에 `max`/`min`이 필요없음
- 샘플러는 데이터가 아니라 읽는 방법을 적은 규칙표라서 해제하지 않아도 된다.

> SRV로 읽고 UAV로 쓰는 이유

- `RWTexture2D`로 UAV에서 읽는 것도 가능은 함
- 하지만 D3D11 기본 기능 수준에서 UAV 읽기는 `R32_FLOAT`, `R32_UINT`, `R32_SINT` 같은 단일 32비트 포맷만 지원한다.
- `R8G8B8A8_UNORM` 텍스처는 UAV로 읽을 수 없음
- SRV는 "아무도 안 바꾼다"는 게 보장되어 텍스처 캐시를 마음껏 쓸 수 있어서 읽기가 더 빠르다.
- 샘플링(`Sample`, `SampleLevel`)은 SRV에서만 가능
- 따라서 **읽는 쪽은 SRV, 쓰는 쪽은 UAV**로 나눈다.

</details>

<details>
  <summary> 4. 구조적 버퍼 </summary>

> 필요한 이유

- 텍스처의 한 칸에는 `float4` 같은 색 데이터만 들어간다.
- 파티클처럼 한 칸에 위치, 속도, 수명이 다 들어가야 하는 경우 사용
- C++의 `vector<Particle>`을 GPU에 올린 것이라고 보면 됨

```hlsl
struct Particle
{
    float3 Position;
    float3 Velocity;
    float  Age;
};

StructuredBuffer<Particle>   gInput;    // 읽기 전용 (SRV)
RWStructuredBuffer<Particle> gOutput;   // 읽기/쓰기 (UAV)

[numthreads(64, 1, 1)]
void CS(int3 id : SV_DispatchThreadID)
{
    Particle p = gInput[id.x];                  // id.x번 상자 꺼내기
    p.Position += p.Velocity * gDeltaTime;      // 위치 갱신
    gOutput[id.x] = p;                          // 결과 넣기
}
```

> 만드는 법

```cpp
D3D11_BUFFER_DESC desc{};
desc.ByteWidth           = sizeof(Particle) * 파티클수;
desc.BindFlags           = D3D11_BIND_SHADER_RESOURCE | D3D11_BIND_UNORDERED_ACCESS;
desc.MiscFlags           = D3D11_RESOURCE_MISC_BUFFER_STRUCTURED;   // 구조적 버퍼
desc.StructureByteStride = sizeof(Particle);                         // 상자 하나의 크기
```

- 뷰를 만들 때 `Format`은 `DXGI_FORMAT_UNKNOWN` (색이 아니라 사용자 구조체라서 포맷이 없음)
- SRV는 `D3D11_SRV_DIMENSION_BUFFEREX`, UAV는 `D3D11_UAV_DIMENSION_BUFFER`로 지정하고 원소 개수(`NumElements`)를 넣는다.

> 상수 버퍼와 차이

| |상수 버퍼|구조적 버퍼|
|---|---|---|
|비유|모든 일꾼이 보는 게시판|일꾼마다 하나씩 가져가는 상자 선반|
|크기|작음 (최대 64KB)|큼|
|셰이더에서 쓰기|불가|UAV로 가능|
|용도|행렬, 시간, 설정값|파티클, 대량 데이터|

</details>

<details>
  <summary> 5. 결과를 CPU로 가져오기 </summary>

- GPU 작업용 텍스처/버퍼(`D3D11_USAGE_DEFAULT`)는 CPU가 직접 읽을 수 없다.
- 따라서 스테이징 버퍼(중간 창고)를 거쳐서 가져온다.

```
[GPU 작업 창고]  ──CopyResource──▶  [스테이징 창고]  ──Map──▶  CPU가 읽음
   (DEFAULT)                          (STAGING)
```

```cpp
// 1. 중간 창고 : CPU가 읽을 수 있게
desc.Usage          = D3D11_USAGE_STAGING;
desc.BindFlags      = 0;                        // 파이프라인에는 안 묶음
desc.CPUAccessFlags = D3D11_CPU_ACCESS_READ;

// 2. GPU 결과를 중간 창고로 복사 (목적지, 원본 순서)
m_pContext->CopyResource(pStaging, pGPUResult);

// 3. 잠금 열고 읽기
D3D11_MAPPED_SUBRESOURCE mapped;
m_pContext->Map(pStaging, 0, D3D11_MAP_READ, 0, &mapped);
// ... mapped.pData 읽기 ...
m_pContext->Unmap(pStaging, 0);
```

- `Map`을 하면 CPU가 GPU 작업이 끝날 때까지 기다려야 하기 때문에 느리다.
- 매 프레임 사용하면 안 되고, 디버깅용이나 가끔만 사용
- 그래서 게임 로직에 쓰이는 충돌 같은 건 보통 CPU에서 처리하고, 계산 셰이더는 파티클처럼 결과가 GPU 안에서 끝나는 작업에 사용한다.

</details>

<details>
  <summary> 6. 스레드 식별 시스템 값(시멘틱 값) </summary>

- 예시 : `[numthreads(8, 8, 1)]`, `Dispatch(3, 2, 1)`

```
       팀(0,0)       팀(1,0)       팀(2,0)
     ┌────────┐   ┌────────┐   ┌────────┐
     │ 8×8명  │   │ 8×8명  │   │ 8×8명  │
     └────────┘   └────────┘   └────────┘
       팀(0,1)       팀(1,1)       팀(2,1)
     ┌────────┐   ┌────────┐   ┌────────┐
     │ 8×8명  │   │ 8×8명  │   │ ★     │   ← 팀(2,1)의 (3,5) 자리 일꾼
     └────────┘   └────────┘   └────────┘
```

|번호표|의미|값|
|---|---|---|
|SV_GroupID|우리 팀 번호|(2,1,0)|
|SV_GroupThreadID|팀 안에서의 내 자리|(3,5,0)|
|SV_DispatchThreadID|전체에서 내 위치|(2*8+3, 1*8+5, 0) = (19,13,0)|
|SV_GroupIndex|팀 안 자리를 한 줄로 편 번호|5*8 + 3 = 43|

```
DispatchThreadID = GroupID × 팀크기 + GroupThreadID
GroupIndex       = z × (팀가로 × 팀세로) + y × 팀가로 + x
```

- 텍스처, 버퍼 접근할 때는 `SV_DispatchThreadID`(전체 위치), 공유 메모리 접근할 때는 `SV_GroupThreadID`(팀 안 자리)를 주로 사용
- 필요한 번호표만 매개변수로 받으면 됨. 4개를 다 받을 필요 없음
```hlsl
void CS(int3 groupThreadID    : SV_GroupThreadID,
        int3 dispatchThreadID : SV_DispatchThreadID)
```
</details>

<details>
  <summary> 7. 추가 버퍼와 소비 버퍼 </summary>

> 필요한 이유

- 파티클 중 수명이 다한 것은 버리고 싶은 경우, 구조적 버퍼로 하면 출력 버퍼에 구멍이 생긴다.
- 앞 일꾼들이 몇 개를 버렸는지 모르기 때문에 몇 번 칸에 넣을지 정할 수 없음

> 해결책

- 칸 번호 없이 상자 더미처럼 쓰는 버퍼를 사용한다.
```hlsl
ConsumeStructuredBuffer<Particle> gInput;    // 꺼내 쓰는 더미
AppendStructuredBuffer<Particle>  gOutput;   // 던져 넣는 더미

[numthreads(64, 1, 1)]
void CS()
{
    Particle p = gInput.Consume();     // 더미에서 아무거나 하나 꺼냄

    p.Position += p.Velocity * gDeltaTime;
    p.Age      += gDeltaTime;

    if (p.Age < gMaxAge)               // 살아 있으면
        gOutput.Append(p);             // 출력 더미에 넣음, 죽었으면 안 넣음 -> 버려짐
}
```

- GPU가 내부적으로 카운터(몇 개 들어있는지)를 관리해서 일꾼들이 동시에 넣고 꺼내도 겹치지 않는다.
- UAV를 만들 때 `D3D11_BUFFER_UAV_FLAG_APPEND` 플래그가 필요
- 처음에 몇 개 들어있는지는 `CSSetUnorderedAccessViews`의 마지막 인자로 알려준다.
- 크기는 고정이라 자동으로 늘어나지 않음. 꽉 찼는데 넣거나, 비었는데 꺼내면 안 된다.
- 순서가 보장되지 않기 때문에 순서가 중요한 데이터에는 사용하면 안 됨

</details>

<details>
  <summary> 8. 공유 메모리와 동기화 </summary>

> 필요한 이유

- 같은 데이터를 여러명이 따로 가져오는 낭비를 줄이기 위해
- 블러의 경우 각 스레드(일꾼)들은 자기 픽셀의 좌우 이웃 5개씩 총 11개를 읽는다.
- 같은 물건을 11명이 각자 가져오는 것은 낭비

> 해결책

- 팀 작업대에 한 번만 가져다 놓기
```hlsl
groupshared float4 g_Cache[256 + 10];
```

- `groupshared`로 선언한 변수는 같은 스레드 그룹의 스레드들이 같이 쓰는 작업대.
- 셰이더 코드에는 한 번만 선언하지만 실제로는 스레드 그룹(팀)마다 작업대가 따로 있고 다른 스레드 그룹의 작업대는 볼 수 없다.
- 작업대는 팀이 일하는 동안만 존재하고, 다음 `Dispatch`에는 새 작업대를 받는다.
- 크기 제한이 있다.(스레드 그룹당 32KB)

> 작업 순서

```
1. 각자 창고(Texture2D g_Input)에서 각자 맡은 픽셀을 가져와서 작업대에 올려놓음
2. 작업대(공유 메모리)가 다 차기 전까지는 어떤 스레드(일꾼)도 다음 단계로 넘어가지 않음 -> GroupMemoryBarrierWithGroupSync();
3. 작업대에서 이웃 11개를 꺼내서 계산
```

- 공유메모리`groupshared`를 사용하면 항상 `GroupMemoryBarrierWithGroupSync()` 이 장벽이 짝으로 따라온다.
- 쓰기 단계와 읽기단계 사이에 반드시 장벽을 세워야 한다.
- 장벽은 같은 팀 안에서만 동작한다. 다른 팀은 기다리지 않음
- 팀 사이에 순서가 필요하면 `Dispatch`를 나눠서 호출해야 한다. (가로 패스, 세로 패스를 따로 `Dispatch`하는 이유)

</details>

  <summary> 9. 블러 예제1 - 이웃과 섞기 </summary>

- 블러 : 각 픽셀을 이웃들의 평균으로 바꾸기
```
원본 한 줄:       [ 0,  0,  9,  0,  0 ]
3칸 평균 블러:    [ 0,  3,  3,  3,  0 ]   ← 9가 주변으로 번짐
```
- 가중 평균 : 가까울 수록 많이 섞기 (가우스 블러)
```
이웃 위치:  -5   -4   -3   -2   -1   [나]  +1   +2   +3   +4   +5
가중치:    0.05 0.05 0.1  0.1  0.1  0.2  0.1  0.1  0.1  0.05 0.05
```
- 가중치의 합은 반드시 1이어야 한다. 1보다 크면 블러할수록 밝아지고, 작으면 어두워짐

- 가우스 블러는 분리 가능 블러이다.
- 가로로 한번 블러하고, 세로로 한 번 나눠서 블러해도 결과가 똑같은 성질이 있다.
- 반지름 5 기준 사방 이웃을 한 번에 섞으면 11 × 11 = 121개, 나눠서 하면 11 + 11 = 22개만 읽으면 됨

</details>

  <summary> 10. 블러 예제2 - 텍스처로 렌더링 </summary>

> Render-to-Texture

- 후면버퍼는 블러할 수 없다.
- 텍스처가 있어야 계산 셰이더에서 읽을 수 있다.
- 따라서 `render-to-texture`(RenderTarget)를 이용하여 UI 이전까지의 장면을 오프스크린 텍스처에 먼저 그린다.
- 그 후 다시 백버퍼로 `RenderTarget`을 바꾼 뒤 오프스크린 텍스처를 백버퍼에 그린다.
- 이때 백버퍼에 그리기 전에 ComputeShader로 블러효과를 준 뒤 그리면 된다.
- 오프스크린 텍스처는 RTV(장면 그리기), UAV(블러 결과 쓰기), SRV(읽기) 세 가지 뷰가 필요함

> 구현 개요

- 원본을 읽으면서 같은 텍스처에 결과를 쓰면 원본이 망가지고, 한 텍스처를 SRV(입력)와 UAV(출력)에 동시에 묶을 수 없다.
- 그래서 읽는 텍스처와 쓰는 텍스처를 나눠 A ↔ B로 번갈아 쓴다(핑퐁).
```
가로 패스:  A를 읽어서 → B에 씀    (A: SRV, B: UAV)
세로 패스:  B를 읽어서 → A에 씀    (B: SRV, A: UAV)
```
- 한 바퀴가 항상 A → B → A로 끝나기 때문에 몇 번을 반복해도 최종 결과는 A에 있다.
- 패스 사이에는 반드시 SRV, UAV를 nullptr로 뽑아야 함

> Dispatch 개수

| |팀 모양|Dispatch(1280 x 720)|
|---|---|---|
|가로 패스|`numthreads(256,1,1)` 가로 한 줄|`(5, 720, 1)`|
|세로 패스|`numthreads(1,256,1)` 세로 한 줄|`(1280, 3, 1)`|

```
가로 팀 수 = (1280 + 255) / 256 = 5
세로 팀 수 = (720 + 255) / 256 = 3    -> 3 × 256 = 768명, 48명은 화면 밖 (쓰기가 무시되므로 문제없음)
```

</details>

  <summary> 11. 블러 예제3 - BlurFilter 클래스 </summary>

> BlurFilter 클래스

- 텍스처를 하나 받아서 그 텍스처를 흐리게 만들어 주는 도구
- 멤버변수 : 텍스처 B(중간 저장소)의 SRV, UAV와 계산 셰이더 2개(가로, 세로)
- 텍스처 A는 렌더러가 가지고 있고, BlurFilter는 잠깐 빌려서 사용만 한다.
- 멤버 함수 : `BlurInPlace(A의 SRV, A의 UAV, 반복 횟수)`
- `BlurInPlace()` 함수는 A 텍스처를 입력하면 블러효과를 반복 횟수만큼 적용해서 A에 다시 담아준다. (InPlace = 제자리에서)
- 렌더러는 B가 있는지, Dispatch를 몇 번 하는지 몰라도 됨

```cpp
for (uint32_t i = 0; i < iBlurCount; ++i)
{
    // 가로 : A(SRV) -> B(UAV)
    m_pContext->CSSetShader(m_pCS_Horz.Get(), nullptr, 0);
    m_pContext->CSSetShaderResources(0, 1, &pInputSRV);
    m_pContext->CSSetUnorderedAccessViews(0, 1, m_pUAV_B.GetAddressOf(), nullptr);
    m_pContext->Dispatch(iNumGroupsX, m_iHeight, 1);
    // 해제

    // 세로 : B(SRV) -> A(UAV)
    m_pContext->CSSetShader(m_pCS_Vert.Get(), nullptr, 0);
    m_pContext->CSSetShaderResources(0, 1, m_pSRV_B.GetAddressOf());
    m_pContext->CSSetUnorderedAccessViews(0, 1, &pInputUAV, nullptr);
    m_pContext->Dispatch(m_iWidth, iNumGroupsY, 1);
    // 해제
}
m_pContext->CSSetShader(nullptr, nullptr, 0);
```

- 렌더러에서는 후면버퍼로 RenderTarget을 되돌린 **뒤에** 호출해야 한다. A가 RTV로 묶여 있는 상태에서 UAV로 묶으면 무시됨

  <summary> 12. 블러 예제4 - 계산 셰이더 </summary>

> 공유 메모리 준비

- 팀이 맡은 픽셀은 256개 이지만 양 끝 픽셀도 바깥 이웃 5개가 필요하기 때문에 CacheSize는 266개가 된다.

```hlsl
#define N 256
#define CacheSize (N + 2 * gBlurRadius)    // 256 + 10 = 266칸
groupshared float4 gCache[CacheSize];
```

```
팀 (2, y)가 맡은 픽셀:        512 ─────── 767
필요한 픽셀:        507~511 | 512 ─────── 767 | 768~772
gCache 칸 번호:     [0 ~ 4] | [5 ───── 260] | [261 ~ 265]
                   왼쪽 이웃     내 픽셀들       오른쪽 이웃
```

- 다른 팀의 작업대는 볼 수 없기 때문에 경계 이웃은 각 팀이 직접 가져옴 (이웃 팀과 겹치는 10칸은 두 번 읽음)

> 공유 메모리 채우기

```hlsl
// 왼쪽 5명(0~4번)은 왼쪽 이웃도 하나씩 더 가져옴
if (groupThreadID.x < gBlurRadius)
{
    int x = max(dispatchThreadID.x - gBlurRadius, 0);       // 화면 왼쪽 끝 넘으면 0으로
    gCache[groupThreadID.x] = gInput[int2(x, dispatchThreadID.y)];
}

// 오른쪽 5명(251~255번)은 오른쪽 이웃도 하나씩 더 가져옴
if (groupThreadID.x >= N - gBlurRadius)
{
    int x = min(dispatchThreadID.x + gBlurRadius, gInput.Length.x - 1);   // 오른쪽 끝 넘으면 끝으로
    gCache[groupThreadID.x + 2 * gBlurRadius] = gInput[int2(x, dispatchThreadID.y)];
}

// 전원이 자기 픽셀을 가져옴 (작업대 왼쪽 5개 넣을 공간이 필요하니까 5칸 밀어서)
gCache[groupThreadID.x + gBlurRadius] = gInput[min(dispatchThreadID.xy, gInput.Length.xy - 1)];

// 다같이 기다리기
GroupMemoryBarrierWithGroupSync();
```

- `gInput.Length` : 텍스처 크기 (1280, 720). `GetDimensions(iWidth, iHeight)`로도 구할 수 있음
- 작업대는 팀 안 번호(`groupThreadID`), 텍스처는 전체 번호(`dispatchThreadID`)로 접근한다.
- 화면 밖 스레드도 `return`하면 안 되고 장벽까지 같이 가야 한다. (장벽에서 전원 도착을 영원히 기다리게 됨)

> 가중평균으로 픽셀의 색 계산

```hlsl
float4 blurColor = float4(0, 0, 0, 0);

[unroll]
for (int i = -gBlurRadius; i <= gBlurRadius; ++i)
{
    int k = groupThreadID.x + gBlurRadius + i;          // 작업대에서 이웃 위치
    blurColor += gWeights[i + gBlurRadius] * gCache[k];
}
// 결과 쓰기(UAV)
gOutput[dispatchThreadID.xy] = blurColor;
```

- `i` : 나로부터 몇 칸 떨어진 이웃인지 (-5 ~ +5)
- `k` : 내 픽셀이 있는 작업대 칸(`groupThreadID.x + 5`)에서 `i`만큼 이동한 칸
- `gWeights[i + gBlurRadius]` : `i`가 음수가 될 수 있어서 +5를 해서 0~10으로 옮김
- `[unroll]` : 반복문을 펼쳐서 11줄짜리 코드로 만들라는 지시. 반복 횟수가 고정이라 가능하고 조금 빨라짐

> 세로 블러

- 가로 블러에서 x와 y만 바꾼 것
- 팀 모양 `numthreads(1, N, 1)`, 이웃은 위아래, `gInput.Length.y` 사용

</details>

  <summary> 13. 블러 예제5 - 버텍스, 인덱스 버퍼 없이 화면 전체 그리기  </summary>

> 개요

- `Draw(3, 0)`을 호출하면 입력 조립기(IA)가 정점 셰이더를 3번 호출하면서 `SV_VertexID`로 0,1,2번호를 자동으로 붙여준다.
- 정점  셰이더가 이 번호만 보고 꼭짓점 위치를 직접 계산한다.
- 정점 데이터를 메모리에서 읽지 않으므로 정점 버퍼, 인덱스 버퍼, 입력 레이아웃이 모두 필요없음.
- `VS_IN`이 없는 이유도 같다. `VS_IN`은 정점 버퍼를 해석하는 구조체인데 읽을 정점 버퍼가 없기 때문

> 사각형이 아닌 큰 삼각형으로 그리는 이유

```
 (-1,1)          (1,1)          (3,1)
   0 ●━━━━━━━━━━━━┯━━━━━━━━━━━━━● 1
     ┃   화면     │          ╱
     ┃  [-1,1]²   │       ╱
     ┃            │    ╱
     ┠────────────┘ ╱  ← 화면 우하단(1,-1)이 빗변 위에 딱 걸림
     ┃           ╱
     ┃        ╱
     ┃     ╱
   2 ●
 (-1,-3)
```

- 화면(NDC -1 ~ 1)을 완전히 덮는 직각삼각형이 된다.
- 화면 밖 부분은 래스터라이저가 클리핑으로 잘라내므로 픽셀 비용이 들지 않음
- 삼각형 2개를 그려야하는 사각형보다 정점이 적고 가운데 대각선 이음매가 없다.

> 정점 셰이더

```hlsl
struct VS_OUT
{
    float4 vPosition : SV_POSITION;
};

VS_OUT VS_FullScreen(uint iVertexID : SV_VertexID) //<- 여기에 호출될 때마다 0, 1, 2가 입력 됨
{
    VS_OUT Out;

    float2 g_vUVs[3] = { float2(0, 0), float2(2, 0), float2(0, 2) };
    float2 vUV = g_vUVs[iVertexID];

    // 이미 클립 공간 좌표를 직접 만들었으므로 월드,뷰,투영 행렬을 곱하지 않음
    // w = 1이라 원근나눗셈을 해도 값이 그대로임.
    // z = 0 이므로 c++에서 깊이 테스트를 끄고 그려야 뒷 부분 UI가 가려지지 않음.

    Out.vPosition = float4(vUV * float2(2.f, -2.f) + float2(-1.f, 1.f), 0.f, 1.f); 
    return Out;
}
```

|iVertexID|vUV|NDC|
|---|---|---|
|0|(0, 0)|(-1, 1) 화면 좌상단|
|1|(2, 0)|(3, 1) 오른쪽 바깥|
|2|(0, 2)|(-1, -3) 아래쪽 바깥|

- UV는 아래로, NDC는 위로 증가하기 때문에 y에 -2를 곱해서 뒤집는다.
- 0 -> 1 -> 2가 화면에서 시계방향이라 컬링되지 않음

> 픽셀 셰이더

```hlsl
float4 PS_FullScreen(VS_OUT In) : SV_TARGET
{
    return g_Input[uint2(In.vPosition.xy)];
}
```

- 정점 셰이더에서 내보낸 `SV_POSITION`은 클립 공간 좌표였으나 래스터라이저를 거친 뒤 픽셀 셰이더로 들어오는 값은 화면 픽셀 좌표(뷰포트 변환 결과)이다.
- (0.5, 0.5), (1.5,0.5)와 같은 픽셀 중심 값이 들어온다.
- `uint2`로 바꾸면 소수점이 잘려 정확한 텍셀 인덱스가 되고 텍스처 크기와 화면 크기가 같기 때문에 샘플러 없이 읽을 수 있다.

> C++ 코드

- 초기화
```cpp
// VS, PS 컴파일 + 생성  ("VS_FullScreen"/"vs_5_0", "PS_FullScreen"/"ps_5_0")
// 입력 레이아웃은 만들지 않음

D3D11_DEPTH_STENCIL_DESC noDepth{};
noDepth.DepthEnable = FALSE;                // 깊이 테스트, 깊이 쓰기 모두 끔
m_pDevice->CreateDepthStencilState(&noDepth, &m_pDSS_NoDepth);
```

- 그리기(DrawFullScreen)
  
```cpp
m_pContext->OMSetDepthStencilState(m_pDSS_NoDepth.Get(), 0);   // 깊이 끄기

m_pContext->IASetInputLayout(nullptr);                          // 입력 레이아웃 없음
m_pContext->IASetPrimitiveTopology(D3D11_PRIMITIVE_TOPOLOGY_TRIANGLELIST);

m_pContext->VSSetShader(m_pVS_FullScreen.Get(), nullptr, 0);
m_pContext->PSSetShader(m_pPS_FullScreen.Get(), nullptr, 0);
m_pContext->PSSetShaderResources(0, 1, m_pSceneSRV.GetAddressOf());

m_pContext->Draw(3, 0);                                         // 정점 3개

ID3D11ShaderResourceView* pNullSRV[1] = { nullptr };
m_pContext->PSSetShaderResources(0, 1, pNullSRV);               // SRV 해제
m_pContext->OMSetDepthStencilState(nullptr, 0);                 // 깊이-스텐실 상태 복구
```

- SRV를 해제하는 이유 : 다음 프레임에 같은 텍스처를 RTV로 묶을 때 입력/출력 동시 바인딩이 되기 때문
- 해제가 필요한 건 RTV나 UAV로 다시 묶일 수 있는 텍스처뿐이다. DDS처럼 SRV만 있는 텍스처는 해제하지 않아도 됨

</details>
