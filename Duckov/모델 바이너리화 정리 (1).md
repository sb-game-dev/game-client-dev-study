# 모델 바이너리화 정리 (1) — 파일 입출력부터 ModelConverter 준비까지

## 0. 왜 바이너리화를 하나

### 0-1. FBX와 assimp는 무엇인가
- **FBX**는 모델링 툴(Maya, Blender, 3ds Max 등)끼리 모델을 주고받기 위한 **교환용 포맷**이다. 메시, 머티리얼, 뼈, 애니메이션, 카메라, 조명, 툴 전용 설정까지 담을 수 있게 만들어져서 구조가 크고 복잡하다.
- **assimp**(Open Asset Import Library)는 FBX, OBJ, glTF 등 수십 가지 포맷을 읽어서 **`aiScene`이라는 하나의 공통 구조**로 바꿔주는 라이브러리다.
- 즉 FBX는 "게임이 바로 쓰기 좋은 모양"이 아니라 "툴끼리 정보를 잃지 않고 주고받기 좋은 모양"이다.

### 0-2. 지금 엔진이 모델을 읽는 과정
```
CModel::Create("xxx.fbx")
  └ Initialize_Prototype
      ├ m_pImporter.ReadFile(경로, 플래그)   ① FBX 해석 → aiScene 생성
      ├ Ready_Bones(mRootNode)              ② 노드 트리를 돌며 CBone 생성
      ├ Ready_Meshes(...)                   ③ aiMesh마다 CMesh 생성
      │    └ 정점을 VTXMESH 배열로 복사 → 정점 버퍼(GPU)
      │    └ 면(mFaces)을 인덱스 배열로 펴기 → 인덱스 버퍼(GPU)
      └ Ready_Materials(...)                ④ aiMaterial마다 CMaterial 생성
           └ 텍스처 파일 이름 추출 → 경로 조립 → SRV 생성
```

①에서 `ReadFile`은 단순히 파일을 읽는 게 아니라 **플래그에 적힌 후처리까지** 매번 다시 한다.

| 플래그 | assimp가 매번 하는 일 |
|---|---|
| `aiProcess_ConvertToLeftHanded` | 오른손 좌표계 → DirectX의 왼손 좌표계로 정점, 면 방향 변환 |
| `aiProcessPreset_TargetRealtime_Fast` | 사각형 면을 삼각형으로 쪼개기, 노멀/탄젠트 계산, 중복 정점 합치기 등 |
| `aiProcess_PreTransformVertices` (NONANIM) | 노드 계층의 변환을 정점에 미리 곱하기 |

### 0-3. 지금 방식의 문제
1. **느리다.** 위 해석과 후처리를 **게임을 켤 때마다, 모델마다** 반복한다. 결과는 매번 똑같은데도 그렇다. 모델이 많아질수록 로딩이 길어진다.
2. **메모리를 두 번 쓴다.** `CModel`이 `Assimp::Importer`를 **멤버 변수로** 들고 있다. Importer가 살아 있는 동안 `aiScene`도 메모리에 남아 있어서, GPU 버퍼로 옮긴 뒤에도 원본 데이터가 계속 메모리를 차지한다.
3. **클라이언트가 assimp에 묶인다.** 게임 실행 파일 옆에 assimp dll이 항상 있어야 하고, 엔진 헤더(`Engine_Defines.h`)를 통해 클라이언트 코드까지 assimp 헤더를 보고 컴파일된다.

### 0-4. 해결: "변환"과 "실행"을 나눈다
```
[변환: 한 번만]  FBX → assimp(해석+후처리) → 엔진이 쓰는 데이터만 골라서 → .bin 저장
[실행: 매번]     .bin → 그대로 메모리에 올림 → CreateBuffer   (assimp 불필요)
```
- 무거운 일(FBX 해석, 좌표계 변환, 삼각형화, 탄젠트 계산, 면을 인덱스 배열로 펴기)은 **변환할 때 한 번만** 한다.
- `.bin`에는 **후처리가 끝난 결과**가 들어 있으니, 실행할 때는 **읽어서 GPU로 넘기기만** 한다.
- 참고로 상용 엔진도 같은 방식이다. Unity는 FBX를 프로젝트에 넣으면 내부 포맷으로 변환해서 `Library` 폴더에 저장해두고, 게임은 그 변환된 데이터를 읽는다.

| | 지금 (FBX 직접) | 바꾼 뒤 (.bin) |
|---|---|---|
| 로딩 | 해석 + 후처리 매번 | 읽기만 |
| 메모리 | aiScene이 계속 남음 | 읽고 나면 임시 배열만 해제 |
| 클라이언트의 assimp | 필요 | 필요 없음 |
| 파일 내용 | 툴용 정보까지 전부 | 엔진이 쓰는 것만 |

## 1. 파일 입출력 기본 개념

### 1-1. 바이트와 16진수
- 컴퓨터가 다루는 가장 작은 단위는 **비트**(0 또는 1)이고, 비트 8개를 묶은 것이 **바이트**다.
- 바이트 하나는 0~255 사이의 값을 가진다.
- 바이트를 표기할 때는 보통 **16진수**를 쓴다. 16진수는 0~9, a~f(10~15)로 한 자리를 나타내서, **바이트 하나가 정확히 두 자리(`00`~`ff`)** 로 표현된다.
  - 예: `0x03` = 3, `0x0a` = 10, `0x40` = 64, `0xff` = 255
  - `0x`는 "16진수다"라는 표시다.
- 그래서 바이너리 파일을 볼 때는 `87 d6 12 00`처럼 두 자리씩 끊어서 본다.

### 1-2. 변수는 메모리에 "바이트 몇 개"로 들어 있다
모든 변수는 메모리에서 정해진 개수의 바이트를 차지한다. 그 개수가 `sizeof`다.

| 타입 | sizeof | 비고 |
|---|---|---|
| `char` | 1 | 글자 하나 |
| `int32_t`, `uint32_t` | 4 | 개수, 인덱스 |
| `float` (`f32_t`) | 4 | |
| `XMFLOAT2` | 8 | float 2개 |
| `XMFLOAT3` | 12 | float 3개 |
| `XMFLOAT4X4` | 64 | float 16개 |
| `VTXMESH` | 56 | XMFLOAT3 ×4 + XMFLOAT2 |

- 예를 들어 `int32_t iNum = 1234567;`은 메모리에 `87 d6 12 00` 4바이트로 들어 있다.
- **바이트 순서가 거꾸로 보이는 이유**: 1234567을 16진수로 쓰면 `0x0012D687`인데, x86 CPU는 **낮은 자리 바이트부터** 메모리에 놓는다. 이를 **리틀 엔디언**이라고 한다. 같은 PC에서 쓰고 읽으면 자동으로 맞으니 신경 쓰지 않아도 된다.
- `float`도 4바이트이지만 정수와 저장 방식이 다르다(IEEE 754 규격). 계산할 필요는 없고 "1.0f는 `00 00 80 3f`" 정도만 알아두면 파일을 볼 때 도움이 된다.

### 1-3. 파일 = 바이트가 한 줄로 늘어선 것
- 파일은 바이트가 처음부터 끝까지 한 줄로 이어진 것이다.
- 파일 안에는 "여기는 정점 개수", "여기서부터 이름" 같은 **칸 구분이 없다.**
- 어떤 바이트가 무슨 의미인지는 **쓰는 쪽과 읽는 쪽의 약속(포맷)** 으로만 정해진다.
- 그래서 바이너리화의 핵심은 코드보다 먼저 **"어떤 순서로 무엇을 쓸지" 약속을 정하는 것**이다 (3장).

### 1-4. 텍스트 저장 vs 바이너리 저장
정점 위치 `(1.5, 2.25, -3.0)` 하나를 저장한다고 하자.

| | 텍스트 | 바이너리 |
|---|---|---|
| 저장 내용 | 문자 `1.5 2.25 -3` + 줄바꿈 | float 3개의 메모리 12바이트 |
| 크기 | 숫자 자릿수에 따라 달라짐 | 항상 12바이트 |
| 읽을 때 | 공백을 찾고, 문자를 숫자로 바꾸는 계산(파싱) | 12바이트를 그대로 복사 |
| 메모장으로 열면 | 읽힌다 | 깨져 보인다 |

- 정점이 수만 개면 텍스트는 수만 번 파싱해야 하지만, 바이너리는 **배열 전체를 한 번에 복사**하면 끝난다.
- 바이너리 저장은 **메모리를 사진 찍듯 그대로 파일에 붙여넣는 것**이다. 읽을 때는 그 사진을 다시 메모리에 붙여넣는다.

### 1-5. 반드시 지킬 규칙 3개

**규칙 ① 쓴 순서 그대로 읽는다.**
- 파일에 칸 구분이 없으니, 읽는 쪽은 "쓸 때 이 순서였다"는 약속만 믿고 읽는다.
- `int → float` 순으로 썼는데 `float → int` 순으로 읽으면, **에러 없이** 엉뚱한 값이 들어간다. 에러가 안 나서 더 찾기 어렵다.

**규칙 ② 길이가 변하는 데이터는 개수를 먼저 쓴다.**
- 정점 배열을 읽는 쪽은 정점이 몇 개인지 알 수 없다.
- 그래서 **개수(uint32) → 데이터** 순서로 쓴다. 읽는 쪽은 개수를 먼저 읽고, 그만큼 공간을 만든 뒤 데이터를 읽는다.
- 문자열도 같다. **길이 → 글자들.**

**규칙 ③ 포인터(주소)는 저장하지 않는다.**
- 주소는 "이번 실행에서 이 데이터가 메모리 몇 번지에 있다"는 뜻이다. 다음 실행 때 그 번지에는 아무것도 없다.
- 그런데 겉보기엔 데이터 같지만 **속은 주소인 타입**이 많다.

| 타입 | 실제로 들어 있는 것 | 저장 방법 |
|---|---|---|
| `vector<T>` | 데이터가 있는 주소, 크기, 용량 (24바이트) | `data()`가 가리키는 실제 원소들을 쓴다 |
| `string` | 글자가 있는 주소 등 | `data()`의 글자들을 쓴다 |
| `shared_ptr`, `ComPtr` | 객체의 주소 | 저장 불가 |
| GPU 버퍼, SRV | GPU 쪽 자원 | 저장 불가 → **재료(정점 배열, 텍스처 경로)** 를 저장하고 로드할 때 다시 만든다 |
| `VTXMESH` | float만 들어 있음 | **통째로 써도 된다** |

## 2. C 표준 파일 입출력 (fopen 계열) + 실습

### 2-1. 파일을 다루는 흐름
어떤 방식이든 파일 입출력은 항상 이 세 단계다.
```
열기 (어떤 파일을, 쓰기용/읽기용으로)  →  쓰기 또는 읽기 (여러 번)  →  닫기
```

### 2-2. 도구 하나씩 보기

**`FILE*` — 파일 핸들**
```cpp
FILE* pFile = nullptr;
```
- `FILE`은 "열려 있는 파일 하나"를 나타내는 구조체다. 안을 직접 건드릴 일은 없다.
- **파일을 가리키는 리모컨**이라고 생각하면 된다. 열기에 성공하면 생기고, 쓰기/읽기/닫기를 할 때마다 넘겨준다.

**`_wfopen_s` — 열기**
```cpp
errno_t err = _wfopen_s(&pFile, L"../Bin/Test.bin", L"wb");
```
- 이름 풀이: `f`(file) + `open` + `w`(wide 경로) + `_s`(secure, 안전 버전)
  - **wide**: 경로를 `wchar_t` 문자열(`L"..."`)로 받는다. 엔진이 경로를 `TEXT()`/`wstring`으로 다루고 있고, 한글 폴더명도 안전하다.
  - **_s**: 그냥 `fopen`을 쓰면 MSVC가 "안전하지 않다"는 C4996 경고를 낸다.
- **왜 `&pFile`인가**: 이 함수는 열기에 성공하면 **우리의 `pFile` 변수에 리모컨을 넣어줘야** 한다. 함수가 바깥 변수를 바꾸려면 그 변수의 주소가 필요해서 `&`를 붙인다.
- **반환값 `errno_t`**: **0이면 성공**, 0이 아니면 실패다(폴더가 없음, 다른 프로그램이 파일을 잡고 있음, 읽기용인데 파일이 없음 등).
- **경로**: `../Bin/Test.bin` 같은 상대경로는 exe 위치가 아니라 **작업 디렉터리**(디버깅 속성에서 설정, 6-7 참고)를 기준으로 계산된다.

| 모드 | 뜻 | 파일이 없으면 | 파일이 있으면 |
|---|---|---|---|
| `L"wb"` | write + binary | 새로 만든다 | **내용을 다 지우고** 새로 쓴다 |
| `L"rb"` | read + binary | 실패 | 처음부터 읽는다 |

- **`b`(binary)를 빼면** 텍스트 모드가 된다. 텍스트 모드에서 Windows는 줄바꿈 바이트 `0x0a`를 쓸 때 몰래 `0x0d 0x0a`로 바꾼다. 숫자 데이터 안에 우연히 `0x0a`가 있으면(예: 정수 10) 바이트가 하나 끼어들어서 그 뒤가 전부 밀린다. **바이너리는 항상 `b`.**

**`fwrite` / `fread` — 쓰기, 읽기**
```cpp
size_t fwrite(const void* 주소, size_t 한개크기, size_t 개수, FILE* 파일);
size_t fread (      void* 주소, size_t 한개크기, size_t 개수, FILE* 파일);
```
- `fwrite`: "이 주소부터 `한개크기 × 개수` 바이트를 파일에 복사해라"
- `fread`: "파일에서 `한개크기 × 개수` 바이트를 꺼내 이 주소에 붙여넣어라"
- 주소를 `void*`로 받아서 **어떤 타입이든 캐스팅 없이** 넘길 수 있다.
- 크기와 개수를 따로 받아서 배열에 잘 맞는다: `fwrite(Vertices.data(), sizeof(VTXMESH), 3, pFile)` = "56바이트짜리 3개"
- **반환값 = 실제로 처리한 개수.** 3개를 읽으라고 했는데 2가 돌아오면 파일이 중간에 끝났다(파일이 깨졌거나 순서가 틀렸다)는 뜻이다.
- **파일 커서**: 열린 파일에는 "지금 어디까지 읽었/썼는지" 위치가 있다. `fwrite`/`fread`를 할 때마다 그 바이트 수만큼 자동으로 앞으로 이동한다. 그래서 순서대로 호출만 하면 다음 값이 차례로 나온다(규칙 ①).

**`fclose` — 닫기**
```cpp
fclose(pFile);
```
- `fwrite`는 성능을 위해 바로 디스크에 쓰지 않고 **메모리 버퍼에 모아뒀다가** 한꺼번에 쓴다. `fclose`가 남은 내용을 디스크로 내보내고 파일을 놓아준다.
- 안 닫으면: 마지막 내용이 파일에 안 써질 수 있고, 파일이 계속 잡혀 있어서 다음에 열 때 실패할 수 있다.
- **중간에 `return`하는 경로(실패 처리)에서도 반드시 닫는다.** 가장 많이 빼먹는 곳이다.

### 2-3. 저장 패턴 3가지
| 저장할 것 | 쓰는 순서 | 읽는 순서 |
|---|---|---|
| 값 하나 (int, float, 구조체) | 값 | 값 |
| 배열 (`vector`) | 개수 → `data()`의 원소들 | 개수 → **공간 만들기** → 원소들 |
| 문자열 (`string`) | 길이 → `data()`의 글자들 (`'\0'` 제외) | 길이 → **공간 만들기** → 글자들 |

### 2-4. 실습 코드

**무엇을 하나**: int 하나, float 하나, 정점 3개짜리 배열, 문자열 하나를 파일에 쓰고, 다시 읽어서 같은 값이 나오는지 확인한다. 모델 파일도 결국 이 세 가지 패턴(값, 배열, 문자열)의 조합이다.

**어디에 넣나**: Client의 `CMainApp`에 **멤버 함수 두 개**를 추가하고, `Initialize()`에서 한 번 호출한다. 확인이 끝나면 호출부를 주석 처리하거나 지운다.

**ⓐ `MainApp.h` — 멤버 함수 선언**
```cpp
private:
	HRESULT		Start_Level(LEVEL eStartLevelID);
	HRESULT		Ready_Prototype_For_StaticLV();

	void		Test_Write();
	void		Test_Read();
```
- 기존 `private:` 영역의 `Ready_Prototype_For_StaticLV()` 아래에 두 줄을 추가한다.
- 클래스 안에서만 쓰는 테스트용 함수라 `private`에 둔다.
- 반환형을 `void`로 둔 이유: 실습용이라 실패해도 게임 초기화를 막을 필요가 없고, 결과는 디버거와 콘솔로 확인한다.

**ⓑ `MainApp.cpp` — `Initialize()`에서 호출**
```cpp
    if (FAILED(Start_Level(LEVEL::GAMEPLAY)))
        return E_FAIL;
    if (FAILED(Ready_Prototype_For_StaticLV()))
        return E_FAIL;

    Test_Write();
    Test_Read();

    return S_OK;
}
```
- `Initialize()` 맨 아래, `return S_OK;` 바로 위에 넣는다.
- **반드시 `Test_Write()` → `Test_Read()` 순서.** 파일이 먼저 만들어져야 읽을 수 있다.
- 엔진 초기화 뒤에 두는 이유: Debug 빌드에서는 `Initialize()` 맨 앞의 `AllocConsole()`이 콘솔 창을 열어둔 상태라, ⑧에서 `cout`으로 결과를 바로 볼 수 있다.
- 확인이 끝나면 두 줄을 `//`로 주석 처리한다. 지우지 않고 남겨두면 나중에 다시 실험하기 편하다.

**ⓒ `MainApp.cpp` — 함수 정의**
아래 ①~⑧을 `MainApp.cpp`의 `Ready_Prototype_For_StaticLV()` 정의 아래에 이어서 작성한다. `Engine_Defines.h`가 이미 `<iostream>`, `<vector>`, `<string>` 등을 include하고 있어서 따로 include할 것은 없다.

**① 쓰기 — 열기**
```cpp

{
	FILE* pFile = nullptr;
	if (0 != _wfopen_s(&pFile, L"../Bin/Test.bin", L"wb") || nullptr == pFile)
		return;
```
- 멤버 함수라서 이름 앞에 `CMainApp::`이 붙는다.
- 쓰기+바이너리 모드로 연다. 파일이 없으면 만들고, 있으면 비운다.
- 실패하면 `pFile`이 없으니 닫을 것도 없어서 바로 `return`해도 된다.
- 반환값과 `pFile` 둘 다 검사해서 확실하게 막는다.

**② 쓰기 — 값 하나씩**
```cpp
	int32_t iNum   = 1234567;
	f32_t   fValue = 3.14f;
	fwrite(&iNum,   sizeof(int32_t), 1, pFile);
	fwrite(&fValue, sizeof(f32_t),   1, pFile);
```
- "4바이트짜리 1개를 이 변수 주소에서 복사해라."
- 이 두 줄로 파일에 `87 d6 12 00 c3 f5 48 40` 8바이트가 들어간다.

**③ 쓰기 — 배열**
```cpp
	vector<VTXMESH> Vertices(3);
	Vertices[0].vPosition = { 1.f, 2.f, 3.f };
	Vertices[1].vPosition = { 4.f, 5.f, 6.f };
	Vertices[2].vPosition = { 7.f, 8.f, 9.f };

	uint32_t iNumVertices = static_cast<uint32_t>(Vertices.size());
	fwrite(&iNumVertices,   sizeof(uint32_t), 1,            pFile);
	fwrite(Vertices.data(), sizeof(VTXMESH),  iNumVertices, pFile);
```
- 위치만 넣고 나머지 멤버(노멀, 탄젠트, 바이노멀, UV)는 0이다.
- 개수(3)를 먼저 쓰고(규칙 ②), 정점 3개를 **한 번에** 쓴다.
- `&Vertices`가 아니라 **`Vertices.data()`** 다(규칙 ③). `&Vertices`는 vector 객체 자체(주소, 크기, 용량)의 주소라서 의미 없는 주소값이 저장된다.
- 실제 모델 변환에서도 메시마다 이 두 줄이 그대로 반복된다.

**④ 쓰기 — 문자열, 닫기**
```cpp
	string strName = "Bone_Root";
	uint32_t iLength = static_cast<uint32_t>(strName.size());
	fwrite(&iLength,       sizeof(uint32_t), 1,       pFile);
	fwrite(strName.data(), sizeof(char),     iLength, pFile);
```

- 길이(9)를 쓰고 글자 9개를 쓴다. 끝의 `'\0'`은 쓰지 않는다. 길이를 알고 있으니 필요 없다.
- 텍스처 파일 이름도 나중에 이 방식으로 저장한다.
- 마지막에 `fclose`로 버퍼에 남은 내용을 디스크에 내보낸다.

**⑤ 읽기 — 열기, 값 하나씩**
```cpp

{

	if (0 != _wfopen_s(&pFile, L"../Bin/Test.bin", L"rb") || nullptr == pFile)
		return;

	int32_t iNum   = {};
	f32_t   fValue = {};

	fread(&fValue, sizeof(f32_t),   1, pFile);
```

- 변수를 `{}`로 0 초기화해두면, 읽기가 실패했을 때 쓰레기 값이 아니라 0이 보여서 알아채기 쉽다.
- **쓸 때와 같은 순서(int → float)** 로 읽는다. 커서가 4바이트씩 앞으로 이동한다.

**⑥ 읽기 — 배열**
```cpp
	uint32_t iNumVertices = {};
	fread(&iNumVertices, sizeof(uint32_t), 1, pFile);

	vector<VTXMESH> Vertices(iNumVertices);
	if (iNumVertices != fread(Vertices.data(), sizeof(VTXMESH), iNumVertices, pFile))

```

- `fread`의 반환값으로 3개를 다 읽었는지 확인한다.
- 실패해서 나갈 때도 **`fclose` 후 `return`** 한다.

**⑦ 읽기 — 문자열**
```cpp
	uint32_t iLength = {};
	fread(&iLength, sizeof(uint32_t), 1, pFile);

	string strName(iLength, '\0');
	fread(strName.data(), sizeof(char), iLength, pFile);
```
- 길이만큼 빈 문자열(`'\0'` 9개)을 만들어 공간을 확보하고 거기에 채운다.
- `string::data()`로 글자를 써 넣을 수 있는 건 C++17부터다. 프로젝트가 C++20이라 그대로 된다.

**⑧ 결과 출력, 닫기**

```cpp
	cout << "[Test_Read] iNumVertices : " << iNumVertices << '\n';
```

- Debug 빌드에서 열리는 콘솔 창에 읽은 값을 찍는다. 중단점 없이도 결과를 한눈에 볼 수 있다.
- `Engine_Defines.h`에 `using namespace std;`가 있어서 `std::` 없이 `cout`을 쓴다.
- 출력 앞에 `[Test_Read]`를 붙여두면 다른 로그와 섞여도 찾기 쉽다.
- 출력이 끝난 뒤 `fclose`로 닫는다. 이 줄에 **중단점**을 걸면 지역 창으로도 확인할 수 있다 (2-5의 확인 ①).

### 2-5. 파일이 생긴 뒤 확인하는 방법

**확인 ① 읽은 값 보기 (콘솔 / 디버거)**
- **콘솔**: Debug로 실행(F5)하면 게임 창과 함께 콘솔 창이 뜬다. `[Test_Read]`로 시작하는 줄이 아래 기대 값과 같은지 본다.
- **디버거**: `Test_Read`의 마지막 `fclose(pFile);` 줄에 중단점(F9)을 걸고 실행 → 멈추면 **지역** 창(디버그 → 창 → 지역)을 본다. `Vertices`를 펼치면 노멀, UV 등 나머지 멤버가 0인 것도 확인할 수 있다.
- 기대 값

| 변수 | 기대 값 |
|---|---|
| `iNum` | 1234567 |
| `fValue` | 콘솔 `3.14` / 지역 창 `3.14000010` (float 정밀도 때문에 지역 창에서 끝자리가 보이는 건 정상) |
| `iNumVertices` | 3 |
| `Vertices[0].vPosition` ~ `[2]` | (1,2,3), (4,5,6), (7,8,9) |
| `iLength` | 9 |
| `strName` | "Bone_Root" |

- 값이 다 0이면 → 파일 열기에 실패한 것이다. `_wfopen_s` 줄에서 멈춰서 반환값과 경로를 확인한다.

**확인 ② 파일 크기**
1. 탐색기에서 `Test.bin`을 찾는다 (작업 디렉터리 기준 `../Bin/`).
2. 우클릭 → **속성** → **"크기"** 를 본다. **"디스크 할당 크기"(4KB)가 아니다.**
3. 기대 값: **193바이트**

| 내용 | 바이트 |
|---|---|
| int | 4 |
| float | 4 |
| 정점 개수 | 4 |
| 정점 56 × 3 | 168 |
| 문자열 길이 | 4 |
| "Bone_Root" | 9 |
| **합계** | **193** |

- 크기가 다르면 → 쓴 것과 계산이 다르다는 뜻이다. 0바이트면 `fclose`가 안 불렸을 수 있다.
- **모델 파일도 이렇게 미리 계산해서 실제 크기와 비교한다.** 가장 빠르고 확실한 검증 방법이다.

**확인 ③ 바이트 직접 보기 (Hex 에디터)**
- Visual Studio: **파일 → 열기 → 파일** → `Test.bin` 선택 → **열기** 버튼 옆 **▼** → **연결 프로그램** → **바이너리 편집기**
- 또는 HxD 같은 hex 에디터 프로그램

화면 읽는 법
- **왼쪽 숫자** (`00000000`, `00000010` …): 그 줄이 파일의 몇 번째 바이트부터인지 (16진수). 한 줄에 16바이트라 `0x10`씩 늘어난다.
- **가운데**: 실제 바이트 값
- **오른쪽**: 같은 바이트를 글자로 억지로 보여준 것. 숫자는 의미 없는 기호로 나오고 문자열만 제대로 읽힌다.

기대 결과

| 위치 | 바이트 | 의미 |
|---|---|---|
| `0x00` | `87 d6 12 00` | int 1234567 (리틀 엔디언) |
| `0x04` | `c3 f5 48 40` | float 3.14 |
| `0x08` | `03 00 00 00` | 정점 개수 3 |
| `0x0C` | `00 00 80 3f` `00 00 00 40` `00 00 40 40` + `00` × 44 | 정점[0] 위치 (1, 2, 3) + 나머지 멤버 0 |
| `0x44` | `00 00 80 40` `00 00 a0 40` `00 00 c0 40` + `00` × 44 | 정점[1] (4, 5, 6) |
| `0x7C` | `00 00 e0 40` `00 00 00 41` `00 00 10 41` + `00` × 44 | 정점[2] (7, 8, 9) |
| `0xB4` | `09 00 00 00` | 문자열 길이 9 |
| `0xB8` | `42 6f 6e 65 5f 52 6f 6f 74` | `Bone_Root` (오른쪽 칸에 글자로 보임) |

여기서 확인할 것
- 정점[1]이 `0x0C + 56 = 0x44`, 정점[2]가 `0x44 + 56 = 0x7C`에서 정확히 시작한다 → **`VTXMESH`의 메모리 모양이 그대로 파일에 들어갔다.** 읽어서 그대로 GPU 버퍼에 넘길 수 있다는 뜻이다.
- 화면 어디에도 "여기서부터 정점" 같은 표시가 없다 → `03`이 정점 개수라는 건 **약속**으로만 안다 (1-3).

**확인 ④ 일부러 틀려보기** (하나씩 해보고 원래대로 되돌린다)

| 실험 | 바꿀 곳 | 결과 | 배우는 것 |
|---|---|---|---|
| 순서 바꾸기 | ⑤에서 `fValue`를 `iNum`보다 먼저 읽기 | 에러 없이 두 값이 엉망 | 규칙 ① |
| `fclose` 빼기 | ④의 `fclose` 주석 처리 | 파일이 0바이트이거나 193보다 작을 수 있음 | 버퍼와 닫기 |
| `data()` 대신 `&Vertices` | ③에서 `fwrite(&Vertices, sizeof(Vertices), 1, pFile)` | 파일 크기가 49바이트(=193−168+24)로 변하고 읽은 정점이 엉망 | 규칙 ③ (vector는 주소를 들고 있다) |
| 공간 없이 읽기 | ⑥에서 `vector<VTXMESH> Vertices;` (개수 없이) | 크래시 또는 메모리 오류 | 규칙 ② |

## 3. 모델 파일 포맷

### 3-1. 저장할 것과 안 할 것 (VERSION 1, NONANIM)

| 대상 | 저장 | 이유 |
|---|---|---|
| 메시: 머티리얼 인덱스, 정점, 인덱스 | O | CMesh를 만드는 재료 |
| 머티리얼: 텍스처 종류 + 파일 이름 | O | SRV는 로드할 때 만든다 |
| 뼈(노드) | X | NONANIM은 `aiProcess_PreTransformVertices`로 노드 변환이 정점에 이미 적용된다. 지금 코드도 NONANIM에서는 뼈를 안 쓴다 |
| AABB | X | 로드할 때 정점으로 다시 계산 (계산이 싸다) |
| GPU 버퍼, SRV, 포인터 | X | 규칙 ③ |

### 3-2. 설계 결정
1. **매직 넘버 + 버전을 맨 앞에 둔다.**
   - 매직(`DKMD`): 우리 파일이 아니면 바로 거절한다. 쓰레기 값을 개수로 읽어서 터지는 것을 막는다.
   - 버전: 포맷이 바뀌면 올린다. 옛 파일을 만나면 "다시 변환하세요"라고 알릴 수 있다.
2. **ModelType을 헤더에 둔다.** 지금은 NONANIM만 허용하고, 나중에 ANIM 블록을 붙일 자리로 쓴다.
3. **VertexStride를 메시마다 저장한다.** `VTXMESH` 구조가 바뀌면 로드할 때 잡아내는 안전장치.
4. **문자열은 길이 + 글자로 저장한다.** 고정 길이(`char[MAX_PATH]`)는 낭비가 크다.
5. **텍스처는 실제로 있는 것만, 파일 이름만 저장한다.** 그래서 `.bin`은 FBX와 같은 폴더에 둔다.
6. **텍스처 종류는 엔진 enum(`TEXTURE_TYPE`)으로 저장한다.** `aiTextureType`이 아니므로 나중에 assimp를 빼도 다시 변환할 필요가 없다.
7. **`PreTransformMatrix`는 파일에 굽지 않고 로드할 때 적용한다.**
   - 기준: 항상 똑같이 해야 하는 변환(전치, 면 펴기, 이름을 인덱스로 바꾸기)은 변환기에서 미리 하고, 쓰는 곳마다 달라지는 선택은 로드할 때 한다.

### 3-5. VERSION 2 포맷 (ANIM 추가 시, 예상안)

> 애니메이션을 배우기 전에 만든 **예상안**이다. 수업에서 클래스 구조(뼈, 채널, 키프레임)를 배우면 그에 맞춰 조정한다. 바뀔 수 있는 부분은 3-5-7에 따로 정리했다.

#### 3-5-1. 애니메이션 모델에 추가로 필요한 것

NONANIM은 assimp가 노드 변환을 정점에 미리 곱해줘서(`PreTransformVertices`) **정점만 있으면 그릴 수 있었다.** ANIM은 정점이 뼈를 따라 움직여야 하므로 그 플래그를 쓰지 않고, 대신 다음 정보가 필요하다.

| 필요한 것 | 뜻 | 들어갈 곳 |
|---|---|---|
| **뼈 계층** | 뼈 이름, 부모 뼈, 부모 기준의 기본 변환 행렬 | 뼈 블록 |
| **정점의 뼈 정보** | 이 정점이 어느 뼈(최대 4개)에 얼마만큼(가중치) 붙어 있나 | 정점(`VTXANIMMESH`) 안 |
| **메시가 쓰는 뼈 목록** | 이 메시에 영향을 주는 뼈들의 인덱스 | 메시 블록 |
| **오프셋 행렬** | 정점을 "모델 공간"에서 "그 뼈의 공간"으로 옮기는 행렬 | 메시 블록 |
| **애니메이션** | 시간에 따라 각 뼈가 어디에 있고 어떻게 돌아가 있나 | 애니메이션 블록 |

**용어 풀이**
- **오프셋 행렬(Offset Matrix)**: 모델링할 때의 기본 자세(바인드 포즈)에서 정점을 "뼈 기준 좌표"로 바꿔주는 행렬. 애니메이션 중에는 `정점 × 오프셋 행렬 × 현재 뼈의 최종 행렬` 순으로 곱해서 정점을 움직인다. assimp의 `aiBone::mOffsetMatrix`에 들어 있다.
- **채널(Channel)**: 애니메이션 하나 안에서 **뼈 하나가 시간에 따라 어떻게 움직이는지**의 기록. 걷기 애니메이션이 뼈 30개를 움직이면 채널이 30개다. assimp의 `aiNodeAnim`.
- **키프레임(KeyFrame)**: 채널 안의 **한 순간의 자세**. 크기, 회전, 위치와 그 시각(트랙 위치)을 가진다. 키프레임 사이의 시간은 보간(선형 보간, 구면 보간)으로 채운다.
- **Duration / TicksPerSecond**: 애니메이션 길이를 "틱" 단위로 저장하고, 1초에 몇 틱이 지나가는지를 함께 저장한다. `재생 위치 += TicksPerSecond × 경과 시간(초)`처럼 쓴다.

#### 3-5-3. 블록별 설명

**헤더**
- `Version`이 2가 되고, `ModelType`에 ANIM이 들어올 수 있게 된다.
- `ModelType`을 보고 **뼈 블록과 애니메이션 블록을 읽을지 말지** 정한다. NONANIM이면 이 두 블록이 파일에 아예 없다.

**뼈 블록**
- `CBone`이 가진 값(이름, 부모 인덱스, `m_TransformationMatrix`)을 그대로 옮긴다.
- **순서 = 지금 `Ready_Bones`가 만드는 순서**(노드 트리를 위에서부터 깊이 우선으로 도는 순서). 이 순서에서는 **부모가 항상 자식보다 앞에** 있어서, 실행 중에 뼈 행렬을 앞에서부터 한 번만 돌면서 계산할 수 있다.
- **이름은 저장한다.** 메시와 애니메이션은 이름 대신 인덱스로 뼈를 가리키지만, "오른손 뼈에 무기 붙이기"처럼 게임 코드에서 이름으로 뼈를 찾을 일이 있기 때문이다(`Get_BoneIndex`).
- 행렬은 변환기에서 **전치까지 끝내서** 저장한다 (결정 7의 기준: 항상 똑같이 하는 변환은 미리).
- `m_CombinedTransfromationMatrix`는 실행 중에 계산되는 값이라 저장하지 않는다.

**메시 블록**
- NONANIM이면 VERSION 1과 같다.
- ANIM이면 정점이 `VTXANIMMESH`(88바이트)가 된다. `vBlendIndex`(뼈 번호 4개)와 `vBlendWeight`(가중치 4개)가 정점 안에 들어 있어서 **따로 저장할 필요가 없다.**
- **주의**: 지금 `Ready_Meshes_For_Anim`은 `vBlendWeight`에 값을 넣지 않는다(참고 절의 버그). 변환기에서는 반드시 `mWeights[j].mWeight`를 넣어야 한다. 안 그러면 가중치 0이 파일에 그대로 저장된다.
- `BoneIndex`: 지금 코드는 실행할 때 `Get_BoneIndex(이름)`으로 문자열을 비교해서 찾는다. **변환기에서 미리 찾아서 숫자로 저장**하므로 로드할 때 문자열 비교가 없다.
- `OffsetMatrix`: 지금 코드에는 아직 없다. 애니메이션 수업에서 추가될 가능성이 높아서 미리 자리를 잡았다. `BoneIndex`와 짝으로 붙여서 저장한다.
- `vBlendIndex`의 숫자는 **"이 메시의 뼈 목록(`NumMeshBones`) 안에서 몇 번째"** 다. 모델 전체 뼈 번호가 아니다. 지금 코드도 `vBlendIndex.x = i`(메시 뼈 목록의 i번째)로 넣고 있다.

**머티리얼 블록**
- VERSION 1과 완전히 같다.

**애니메이션 블록**
- 하나의 FBX에 애니메이션이 여러 개 들어 있을 수 있어서 개수부터 쓴다.
- `BoneIndex`: assimp의 채널은 뼈를 **이름**(`mNodeName`)으로 가리킨다. 이것도 변환기에서 **미리 인덱스로 바꿔서** 저장한다.
- **키프레임 합치기**: assimp는 크기 키, 회전 키, 위치 키를 **따로따로, 개수도 다르게** 준다(예: 위치 키 10개, 회전 키 30개). 엔진에서 쓰기 편하도록 변환기에서 **가장 많은 개수에 맞춰 하나의 KEYFRAME 배열로 합친다.** 키가 모자란 쪽은 마지막 값을 그대로 채운다. 이건 "항상 똑같이 하는 변환"이라 변환기에서 미리 한다.
- 회전은 행렬이 아니라 **쿼터니언(float4)** 으로 저장한다. 보간이 쉽고 크기도 작다(행렬 64바이트 vs 쿼터니언 16바이트).

#### 3-5-4. VERSION 1 파일과의 호환

- **NONANIM의 파일 모양은 VERSION 1과 2가 완전히 같다.** 뼈 블록과 애니메이션 블록은 ANIM일 때만 생기기 때문이다.
- 그래서 VERSION 2를 아는 로더는 이렇게 판단한다.

| 파일의 Version | ModelType | 로더 동작 |
|---|---|---|
| 1 | NONANIM | 그대로 읽는다 (다시 변환할 필요 없음) |
| 2 | NONANIM | 그대로 읽는다 |
| 2 | ANIM | 뼈, 애니메이션 블록까지 읽는다 |
| 3 이상 | - | "모르는 버전" → 실패 |

- 규칙: **읽는 쪽은 자기가 아는 버전 이하의 파일은 받아들이고, 모르는 미래 버전은 거절한다.**
- 그러면 VERSION을 왜 올리나? 파일만 보고 "이건 ANIM 형식을 아는 변환기가 만든 파일"이라는 걸 알 수 있고, 나중에 ANIM 부분의 모양을 바꿀 때(예: VERSION 3) 구분할 수 있기 때문이다.

#### 3-5-6. `Model_Format.h`에 추가될 것

```cpp
	struct VERTEX_SKINNED
```

- 엔진에 `static_assert(sizeof(VTXANIMMESH) == sizeof(ModelFile::VERTEX_SKINNED))` 추가.

```cpp
	struct KEYFRAME
```

#### 3-5-7. 수업 후 조정할 수 있는 부분

| 항목 | 지금 예상 | 수업에 따라 바뀔 수 있는 것 |
|---|---|---|
| 오프셋 행렬 | 메시 블록에 `BoneIndex`와 짝으로 | 수업에서 뼈 쪽에 두면 뼈 블록으로 이동 |
| KEYFRAME 모양 | 크기, 회전(쿼터니언), 위치, 시각 | 멤버 순서나 타입이 다르면 엔진 구조체에 맞춤 |
| 키프레임 합치기 | 변환기에서 하나로 합침 | 수업에서 크기/회전/위치 키를 따로 쓰면 따로 저장 |
| 채널이 뼈를 가리키는 방법 | 인덱스 | 수업 코드가 이름을 쓰면 실행 중엔 이름, 파일엔 인덱스로 유지 가능 |
| `PreTransformMatrix` | 로드할 때 적용 (결정 7 유지) | 수업에서 루트 뼈에 곱하는 방식이면 그 방식을 따름 |

→ 어떻게 바뀌든 **"변환기가 쓰는 순서 = 엔진이 읽는 순서"** 와 **"이름 검색, 전치, 합치기처럼 항상 같은 일은 변환기에서 미리"** 라는 원칙만 지키면 된다.

## 4. 전체 구조

### 4-1. 역할 분리
- **변환(FBX → .bin)** 은 별도 콘솔 프로젝트 **ModelConverter**가 맡는다. MapTool은 "배치"라는 원래 역할만 한다.
- **MapTool과 Client는 똑같이** `CModel::Create("xxx.bin")`로 읽는다. 툴과 게임에서 보이는 모델이 같다는 게 보장된다.
- MapTool에는 애니메이션 설정을 넣지 않는다. 변환과 배치는 별개의 결정이다.

### 4-2. 당분간 두 길이 공존한다 (애니메이션 학습 때문)
```
NONANIM:  FBX ─ ModelConverter(assimp) ─▶ .bin ─┐
                                                ▼
                          CModel::Create(eType, 경로)
                           ├ ".bin" → 바이너리 읽기    ← MapTool, Client의 NONANIM 모델
                           └ ".fbx" → 기존 assimp 코드 ← 애니메이션 수업, 테스트
```
- `Create`의 호출 모양은 그대로 두고, 안에서 **확장자로 나눈다.** Loader는 경로 문자열만 바꾸면 된다.
- `Bind_Material(…, aiTextureType, …)` API는 당분간 그대로 둔다. `.bin`을 읽을 때 `TEXTURE_TYPE → aiTextureType` 번역 함수(임시)를 쓴다.
- 코드는 `#pragma region BINARY` / `#pragma region FBX_ASSIMP`로 구역을 나눈다. 나중에 assimp를 뺄 때 지울 곳이 분명해진다.

### 4-3. assimp가 지금 묶여 있는 곳 (나중에 제거할 목록)
- `Engine_Defines.h`의 assimp include 3줄 (Client와 MapTool도 이 헤더를 통해 assimp 헤더를 본다)
- `Engine.vcxproj` 링커 입력의 `assimp-vc143-mt(d).lib`
- `Client/Bin`, `MapTool/Bin`의 `assimp-vc143-mt(d).dll`
- `CModel`의 `aiScene*`, `Assimp::Importer` / `CMesh`, `CMaterial`, `CBone`의 ai 타입 초기화
- `Bind_Material`의 `aiTextureType` 인자, Player, StaticProp, Tree_Instance의 `aiTextureType_DIFFUSE`

### 4-4. 로드맵

| 순서 | 할 일 | 엔진의 assimp |
|---|---|---|
| **변환기 준비** | `Model_Format.h` 만들기, ModelConverter 프로젝트 만들기 ← **이 문서 5~6장** | 유지 |
| 변환 코드 | 나무 FBX 하나를 `.bin`으로 변환, 크기와 hex로 확인 | 유지 |
| 엔진 읽기 | `CModel`에 `.bin` 길 추가, FBX와 `.bin` 나무를 띄워 비교 | 유지 |
| 교체 | Client, MapTool의 NONANIM 모델을 전부 `.bin`으로 | 유지 |
| *(수업)* | 애니메이션은 FBX를 직접 읽으면서 학습 | 유지 |
| ANIM 바이너리화 | 3-5 포맷대로 VERSION 2 구현 (변환기 `--anim`, 엔진 ANIM `.bin` 읽기) | 유지 |
| assimp 제거 | 4-3 목록 제거, `Bind_Material` 인자를 `TEXTURE_TYPE`으로 | **제거** |
| 마무리 | ModelConverter 전용 assimp를 `Game/ThirdParty` 같은 공용 위치로 이동 | - |

## 5. `Model_Format.h` 만들기

### 5-1. 이 파일이 하는 일
ModelConverter는 Engine.dll을 **링크하지 않는다.** GPU도 Device도 필요 없기 때문이다.
대신 3장의 포맷 약속은 엔진과 똑같이 알아야 한다. 그 약속 3가지를 담은 **가벼운 헤더 하나**를 엔진과 변환기가 같이 include한다.

| 약속 | 내용 |
|---|---|
| ① | 매직 넘버, 버전 |
| ② | 텍스처 종류 번호 (`TEXTURE_TYPE`) |
| ③ | 정점 하나의 모양 (`VERTEX_STATIC`, 56바이트) |

### 5-2. 파일 만들기
1. 솔루션 탐색기 → **Engine** 프로젝트 → 헤더 파일이 모여 있는 필터 우클릭 → **추가** → **새 항목**
2. **헤더 파일(.h)** 선택, 이름 `Model_Format.h`
3. **위치를 반드시 `...\Game\Engine\Public\`으로 바꾼다.**
   - Engine 프로젝트 파일은 `Engine\Default\` 안에 있어서, 그대로 두면 `Default` 폴더에 만들어진다.
   - `Public`에 있어야 ① 엔진 빌드 후 EngineSDK로 복사되고 ② ModelConverter의 include 경로(6장)에서 찾을 수 있다.
4. 다른 소스처럼 **CP949** 로 저장한다 (한글 주석이 깨지지 않도록).

### 5-3. 코드

**include — 의존성을 최소로**
```cpp
#pragma once
#include <cstdint>
#include <DirectXMath.h>
```
- `Engine_Defines.h`를 include하지 않는다. d3d11, DirectXTK, dinput 등이 딸려오지 않게 하기 위해서다.
- DirectXMath는 헤더만 있으면 되고 링크가 필요 없다.
- 같은 이유로 엔진 typedef(`char_t` 등) 대신 표준 타입(`char`, `uint32_t`)을 쓴다.

**약속 ① 매직과 버전**
```cpp
namespace Engine::ModelFile
{
	constexpr char		MAGIC[4] = { 'D', 'K', 'M', 'D' };
	constexpr uint32_t	VERSION  = 1;
```
- 변환기는 이 값을 쓰고, 엔진은 읽은 값을 이것과 비교한다.
- 숫자를 양쪽 코드에 따로 적지 않고 반드시 여기서 가져다 쓴다. 버전을 올릴 때도 여기 한 곳만 바꾼다.

**약속 ② 텍스처 종류**
```cpp
	enum class TEXTURE_TYPE : uint32_t
	{
		DIFFUSE,
		NORMALS,
		SPECULAR,
		EMISSIVE,
		END
	};
```
- `aiTextureType` 대신 파일에 저장되는 값이다.
- `: uint32_t` → 파일에 4바이트로 쓰고 읽으므로 크기를 확정해둔다.
- **새 종류는 항상 `END` 바로 앞(맨 뒤)에만 추가한다.** 중간에 끼우면 기존 `.bin`의 번호 의미가 바뀐다. 어쩔 수 없이 바꾸면 VERSION을 올리고 다시 변환한다.
- 변환기: `aiTextureType → TEXTURE_TYPE`으로 번역해서 저장하고, 표에 없는 종류는 건너뛴다.
- 엔진: 당분간 `TEXTURE_TYPE → aiTextureType` 번역 함수(임시)로 기존 `m_Materials` 칸에 넣는다.

**약속 ③ 정점 모양**
```cpp
	struct VERTEX_STATIC
	{
		DirectX::XMFLOAT3	vPosition;
		DirectX::XMFLOAT3	vNormal;
		DirectX::XMFLOAT3	vTangent;
		DirectX::XMFLOAT3	vBinormal;
		DirectX::XMFLOAT2	vTexcoord;
	};
}
```
- `VTXMESH`와 멤버 순서, 타입이 같다 (56바이트).
- `VTXMESH`를 그대로 쓰지 않는 이유: `D3D11_INPUT_ELEMENT_DESC`가 붙어 있어서, 쓰려면 변환기가 d3d11까지 알아야 한다.

### 5-4. 엔진 쪽 안전장치 (나중에 "엔진 읽기" 순서에서 추가)
```cpp
static_assert(sizeof(VTXMESH) == sizeof(ModelFile::VERTEX_STATIC),
              "VTXMESH 와 파일 정점 포맷이 다릅니다");
```
- 같은 모양을 두 곳에 적었으니, 한쪽만 바뀌면 **컴파일 자체가 실패**하게 막는다.
- 파일 안의 `VertexStride`(실행 중 검사)와 함께 이중 안전장치가 된다.
- 지금은 엔진에서 이 헤더를 아무도 include하지 않으므로 엔진 빌드에는 영향이 없다.

## 6. ModelConverter 프로젝트 만들기

### 6-1. 속성 설정이 왜 필요한가
C++ 프로그램은 **컴파일 → 링크 → 실행** 을 거친다. 외부 라이브러리(assimp)를 쓰려면 각 단계에 "어디서 찾아라"를 알려줘야 한다.

| 단계 | 하는 일 | 필요한 파일 | 못 찾으면 |
|---|---|---|---|
| 컴파일 | `.cpp`를 `.obj`로 번역. include한 헤더로 함수의 **선언**을 확인 | 헤더 (`.h`, `.hpp`) | `C1083` |
| 링크 | `.obj`들을 `.exe`로 합침. 함수의 **실제 몸통**이 어디 있는지 연결 | lib | `LNK2019` |
| 실행 | 실제 코드가 든 dll을 메모리에 올림 | dll | "dll을 찾을 수 없습니다" |

- assimp는 **dll 방식**이다. 실제 코드는 dll에 있고, lib(약 590KB)은 "이 함수는 그 dll 안에 있다"는 **목차**만 가지고 있다.
- 그래서 링크할 때는 lib이, 실행할 때는 dll이 필요하다.

**Engine 프로젝트의 기존 설정 (이걸 따라 한다)**

| | Engine 설정 | 실제 위치 |
|---|---|---|
| 헤더 | 추가 포함 디렉터리 `..\Public\` | `Game/Engine/Public/Assimp/` |
| lib | 추가 라이브러리 디렉터리 `../ThirdPartyLib/` | `Game/Engine/ThirdPartyLib/assimp-vc143-mt(d).lib` |
| dll | (엔진은 dll이라 직접 필요 없음) | `Game/Client/Bin/assimp-vc143-mt(d).dll` |

### 6-2. 프로젝트 만들기
1. 솔루션 탐색기 맨 위 **솔루션 'Game'** 우클릭 → **추가** → **새 프로젝트**
2. 검색창에 `콘솔` → **콘솔 앱** (C++) 선택 → 다음
3. 프로젝트 이름 `ModelConverter`, 위치 `...\Duckov\Game\`
4. **만들기** → `Game/ModelConverter/`에 `ModelConverter.vcxproj`, `ModelConverter.cpp`가 생긴다.

### 6-3. 속성 창 열기와 "구성" 고르기 (가장 많이 실수하는 곳)
1. `ModelConverter` 우클릭 → **속성**
2. 창 맨 위 드롭다운 두 개
   - **구성**: `Debug` / `Release` / `모든 구성`
   - **플랫폼**: **반드시 `x64`** (assimp lib이 64비트용이고, 엔진도 x64로만 설정되어 있다)
3. 설정은 **구성마다 따로 저장된다.**
   - 두 구성에 똑같이 들어갈 값 → 구성을 **`모든 구성`** 으로 놓고 입력
   - 구성마다 다른 값(lib 이름) → `Debug`, `Release`를 하나씩 골라서 입력

### 6-4. 공통 설정 (구성: `모든 구성`, 플랫폼: `x64`)

| 메뉴 | 항목 | 값 | 이유 |
|---|---|---|---|
| 구성 속성 → 일반 | 출력 디렉터리 | `$(ProjectDir)Bin\` | exe가 만들어질 폴더 |
| 구성 속성 → 일반 | C++ 언어 표준 | `ISO C++20 표준` | 엔진과 맞춤 |
| C/C++ → 일반 | 추가 포함 디렉터리 | `$(SolutionDir)Engine\Public\` | **컴파일용.** `Assimp/*.h`와 `Model_Format.h`를 둘 다 여기서 찾는다 |
| 링커 → 일반 | 추가 라이브러리 디렉터리 | `$(SolutionDir)Engine\ThirdPartyLib\` | **링크용 (어느 폴더에서)** |

- `$(ProjectDir)` = 이 프로젝트 폴더(`...\Game\ModelConverter\`), `$(SolutionDir)` = 솔루션 폴더(`...\Game\`). VS가 자동으로 채워주는 **매크로**이고, 끝에 `\`가 이미 붙어 있다.
- 절대경로(`C:\Users\...`)를 쓰면 다른 PC에서 깨지므로 매크로를 쓴다.
- 값 클릭 → ▼ → **편집**을 누르면 매크로가 **실제로 바뀐 경로**를 볼 수 있다.

### 6-5. 구성별 설정: 링커 → 입력 → 추가 종속성
기존 값(`%(AdditionalDependencies)`)은 지우지 않고 **맨 앞에** 추가한다.

| 구성 | 맨 앞에 추가 |
|---|---|
| `Debug` | `assimp-vc143-mtd.lib;` |
| `Release` | `assimp-vc143-mt.lib;` |

- **링크용 (어떤 파일을).** 6-4에서 알려준 폴더 안에서 이 이름의 lib을 쓴다.
- 이름 끝의 **`d` = Debug용.** Debug 빌드는 표준 라이브러리 내부 모양이 Release와 달라서 lib도 맞춰야 한다. 엇갈리면 `LNK2038 '_ITERATOR_DEBUG_LEVEL' 불일치` 에러가 난다.

### 6-6. dll 복사 (실행용)
탐색기에서 `Game/Client/Bin/`의 두 파일을 `Game/ModelConverter/Bin/`으로 **복사**한다.
- `assimp-vc143-mtd.dll` (Debug용)
- `assimp-vc143-mt.dll` (Release용)

→ Windows는 exe를 실행할 때 **exe와 같은 폴더**에서 dll을 먼저 찾는다.

### 6-7. 작업 디렉터리 (디버깅 → 작업 디렉터리)
기본값 `$(ProjectDir)` 그대로 둔다. 대신 의미를 알아둔다.

- **작업 디렉터리 = 상대경로의 출발점.** exe 위치가 아니라 이 폴더를 기준으로 계산한다.
```
Game\ModelConverter\  →  ..\     = Game\
                      →  ..\..\  = Duckov\
                      →  ..\..\Resource\  ✔
```
- 그래서 Resource는 `../../Resource/`로 찾아간다. Client가 `../../../Resource/`를 쓰는 것과 깊이가 다른 이유가 이것이다.

### 6-8. 확인용 코드
변환 코드가 아니라 **"설정이 다 맞았나"와 "`Model_Format.h`가 이어졌나"만 확인하는 코드.** `ModelConverter.cpp`의 내용을 지우고 아래를 넣는다.

**include**
```cpp
#include <iostream>
#include "Assimp/Importer.hpp"
#include "Assimp/scene.h"
#include "Assimp/postprocess.h"
#include "Model_Format.h"
```
- 위 세 줄은 엔진의 `Engine_Defines.h`와 같다.
- 마지막 줄은 5장에서 만든 약속 파일이다. 여기서 `C1083`이 나면 6-4 추가 포함 디렉터리나 5-2 파일 위치가 틀린 것이다.

**약속 파일 확인**
```cpp
int main()
{
	using namespace Engine;

	std::cout << "Magic   : " << std::string(ModelFile::MAGIC, 4) << '\n';
	std::cout << "Version : " << ModelFile::VERSION << '\n';
	std::cout << "Vertex  : " << sizeof(ModelFile::VERTEX_STATIC) << " bytes\n";
```
- `DKMD`, `1`, `56 bytes`가 나오면 `Model_Format.h`를 제대로 읽은 것이다.
- 정점 크기가 56이 아니면 구조체 멤버를 잘못 적은 것이다.

**FBX 읽기**
```cpp
	Assimp::Importer Importer;
	const aiScene* pScene = Importer.ReadFile("../../Resource/Mesh/Tree/Pfb_Tree_01_1.fbx",
		aiProcess_ConvertToLeftHanded | aiProcessPreset_TargetRealtime_Fast | aiProcess_PreTransformVertices);

	if (nullptr == pScene)
	{
		std::cout << "읽기 실패: " << Importer.GetErrorString() << '\n';
		return -1;
	}
```
- 엔진 `CModel`의 NONANIM 경로와 **완전히 같은 플래그**다. 다른 플래그로 읽으면 정점이 달라진다.
- 빌드할 때 여기서 `LNK2019`가 나면 6-4 라이브러리 디렉터리나 6-5 추가 종속성이 틀린 것이다.
- `GetErrorString()`은 **왜 실패했는지**(파일 없음, 형식 오류 등)를 알려준다.

**읽은 내용 출력**
```cpp
	std::cout << "메시 개수     : " << pScene->mNumMeshes << '\n';
	std::cout << "머티리얼 개수 : " << pScene->mNumMaterials << '\n';

	for (uint32_t i = 0; i < pScene->mNumMeshes; ++i)
	{
		const aiMesh* pMesh = pScene->mMeshes[i];
		std::cout << "  메시[" << i << "] 정점 " << pMesh->mNumVertices
		          << ", 삼각형 " << pMesh->mNumFaces
		          << ", 머티리얼 " << pMesh->mMaterialIndex << '\n';
	}
	return 0;
}
```
- 3장 포맷 표의 재료(메시 개수, 정점 수, 삼각형 수, 머티리얼 인덱스)를 미리 찍어본다.
- 이 숫자로 `.bin` 크기를 미리 계산해두고, 변환 후 실제 파일과 비교한다.

### 6-9. 실행하기
시작 프로젝트(Client)를 바꾸지 않고 실행하는 방법
1. 툴바에서 `Debug`, `x64` 확인
2. `ModelConverter` 우클릭 → **빌드**
3. `ModelConverter` 우클릭 → **디버그** → **새 인스턴스 시작**

### 6-10. 문제가 생기면

| 증상 | 원인 | 확인할 곳 |
|---|---|---|
| `C1083: 'Assimp/Importer.hpp'` 또는 `'Model_Format.h'`를 열 수 없음 | 헤더를 못 찾음 | 6-4 포함 디렉터리, 5-2 파일 위치, 구성이 `모든 구성`이었는지 |
| `LNK2019: 확인할 수 없는 외부 기호 … Assimp::Importer` | lib을 못 찾음 | 6-4 라이브러리 디렉터리, 6-5 |
| `LNK1104: 'assimp-vc143-mtd.lib'을 열 수 없음` | 폴더나 이름이 틀림 | 6-4 경로, 6-5 철자 |
| `LNK2038: '_ITERATOR_DEBUG_LEVEL' 불일치` | Debug/Release lib이 엇갈림 | 6-5 (Debug에는 `mtd`) |
| `LNK1112: 'x64'와 'x86' 충돌` | 플랫폼이 Win32 | 툴바와 속성의 플랫폼 |
| 실행 시 "dll을 찾을 수 없습니다" | dll 위치 | 6-6 |
| "읽기 실패: Unable to open file" | FBX 경로 | 6-7 작업 디렉터리, 실제 파일 위치 |
| 콘솔 한글이 깨짐 | 새 cpp가 UTF-8로 저장됨 | CP949로 다시 저장하거나 출력 문구를 영어로 |

## 참고: 발견한 기존 코드 이슈
- `CMesh::Ready_Meshes_For_Anim`이 `vBlendIndex`만 채우고 `vBlendWeight`에 `mWeights[j].mWeight`를 넣지 않는다. weight가 항상 0이라 모든 뼈가 `.x` 칸에 덮어써진다. ANIM 바이너리화 전에 고쳐야 한다.
- `Engine.vcxproj` PostBuild 헤더 복사 경로가 Debug는 `EngineSDK\Inc\`, Release는 `EngineSDK\Public\`으로 다르다.
